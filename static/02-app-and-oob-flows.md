# App-based and Out-of-Band Authentication Flows

## Scope and evidence method

This analysis covers Sections 3.1 and 3.2 on physical PDF pages 43-58. The PDF is the normative source. Extracted text was used only for navigation; every page and all sequence figures in the range were inspected directly. Figure 3.1 is on physical page 44 and Figure 3.2 is on physical page 57. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, sections 3.1-3.2, pp. 43-58, Figures 3.1-3.2]

The five evidence categories used below are **Normative Requirement**, **Interpretation**, **Issuer ACS Implementation Consideration**, **Scheme or Vendor Gap**, and **Unresolved**. Requirement levels are stated as **Shall**, **Should**, **May**, **Note**, or **Descriptive (no modal)**. A numbered requirement is cited whenever the source provides one.

The specification describes actions for all involved components, but identifies the 3DS Client (SDK or Method), 3DS Server, DS, and ACS as the four components covered by the Core specification. App implementations must also use the separate SDK Specification for its detailed requirements and implementation guidance. [Normative Requirement; Descriptive (mandatory context)] [EMV 3DS v2.2.0, section 3, p. 43]

## 1. Verified flow boundary and topology

1. **The Requestor Environment topology is not prescribed.** Figure 3.1 is a possible arrangement of the 3DS Requestor App, SDK, and 3DS Server. Its dashed arrows are explanatory and are not EMV 3DS protocol messages. [Interpretation; Note / Descriptive (no modal)] [EMV 3DS v2.2.0, section 3.1, p. 44, Figure 3.1]
2. **The app flow has three protocol routes.** AReq/ARes travels 3DS Server -> DS -> ACS and back; CReq/CRes travels directly SDK <-> ACS; RReq/RRes travels ACS -> DS -> 3DS Server and back. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, section 3.1, p. 44, Figure 3.1; pp. 47-56, Reqs 14, 24, 34, 37, 46, 53, 58, 65, 69, 71, 74, and 77]
3. **Frictionless and challenge share AReq/ARes processing.** Challenge-only processing starts after an ARes with Transaction Status `C`; Steps 10-25 in Figure 3.1 apply only to a Challenge flow. [Normative Requirement; Note / Shall] [EMV 3DS v2.2.0, section 3.1, pp. 44 and 51-52, Req 40]
4. **OOB is a challenge variant, not Decoupled Authentication.** Section 3.2 modifies the standard challenge while retaining CReq/CRes. Decoupled Authentication instead replaces Steps 10-17 and Step 23 with authentication outside the protocol and does not use CReq/CRes. [Interpretation; Note / Descriptive (no modal)] [EMV 3DS v2.2.0, section 3.1, p. 44] [EMV 3DS v2.2.0, section 3.2, pp. 57-58, Figure 3.2]

## 2. App-based frictionless authentication - ordered flow

1. The Cardholder confirms the business action in the 3DS Requestor App. The App identifies the Payment System from the account number and optional cardholder information, calls the SDK `createTransaction` method with Directory Server ID and Message Version, and receives SDK Transaction ID, SDK App ID, Device Information, and the SDK-selected Protocol Version. These are SDK/App actions, not EMV 3DS protocol messages. [Interpretation; Descriptive (no modal) / Note] [EMV 3DS v2.2.0, section 3.1, pp. 44-45]
2. The SDK obtains its device and identity data, generates the SDK Transaction ID, encrypts Device Information with the DS public key, and prepares the SDK-to-ACS secure channel. The SDK Transaction ID uniquely identifies the authentication across AReq/ARes, CReq/CRes, and RReq/RRes from the SDK perspective. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 46, Reqs 2-6]
3. The Requestor Environment makes the SDK data and other required AReq information available to the 3DS Server. App-to-server communication shall use a server-authenticated TLS session. If internal Requestor Environment communication prevents the server from receiving the information within a reasonable time, the App reports that condition to the Cardholder and stops further 3DS processing. [Normative Requirement; Shall / Descriptive consequence] [EMV 3DS v2.2.0, section 3.1, pp. 45-46, Req 1]
4. The 3DS Server verifies the SDK, generates the 3DS Server Transaction ID, obtains required Requestor/server identifiers, chooses the DS, establishes the specified secure link, formats AReq, and sends AReq to the DS. If the Requestor and Server are separate, their data transfer must meet Payment System security requirements with mutual server authentication. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, pp. 46-47, Reqs 7-14 and 300]
5. The DS validates AReq, generates the DS Transaction ID, decrypts and re-encodes SDK Device Information for the ACS, checks version/reference/range conditions, stores the 3DS Server URL with the DS Transaction ID, establishes the specified secure link to the ACS, and forwards AReq. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, pp. 47-48, Reqs 15-24]
6. The ACS validates AReq, checks device/account support, generates the ACS Transaction ID, evaluates the AReq values, and chooses the transaction disposition. For a frictionless transaction the ACS shall not initiate Cardholder interaction; interaction belongs to a Challenge flow. The ACS formats ARes and sends it to the DS. [Normative Requirement; Shall / Should for considering the named Requestor indicators] [EMV 3DS v2.2.0, section 3.1, pp. 48-50, Reqs 25-34, 318, and 386]
7. Before ordinary ARes forwarding, the DS checks the ARes data elements under Req 305. If the ACS Reference Number is not for a participating ACS, the DS shall either return Error Component `D`, Error Code `303` and end processing, or send the 3DS Server an ARes with a Transaction Status defined by the specific DS. The DS otherwise validates and logs the ARes, forwards it unchanged to the 3DS Server, and the 3DS Server validates it. For `Y` or `A`, the server provides the Transaction Status, ECI, and Authentication Value for payment authorisation and passes the necessary ARes information to the Requestor Environment; it then conveys the appropriate response to the App. Req 30 defines `A` as an attempted but not authenticated result, notwithstanding Req 31's “deemed authenticated” wording for ECI/Authentication Value handling. No CReq/CRes or RReq/RRes exchange follows the frictionless result in this flow. [Normative Requirement plus unresolved source tension; Shall / DS-defined alternative] [EMV 3DS v2.2.0, section 3.1, pp. 49-52 and 56, Reqs 30-31, 305, 35-39, and 79]

### 2.1 App Decoupled branch at the common ACS disposition

For an App Decoupled disposition, the ACS shall determine whether an acceptable method is supported based in part on 3DS Requestor Decoupled Max Time, set Transaction Status `D`, set ACS Decoupled Confirmation Indicator `Y`, and store the 3DS Server Transaction ID and DS Transaction ID for later RReq processing. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 50, Req 321]

After the 3DS Server's ARes handling, if the ACS provided Cardholder Information Text for the transaction, the 3DS Server shall ensure that text is displayed on the 3DS Requestor website. The source places this requirement before the note that branches to frictionless, Decoupled, or challenge continuation; the App-oriented use of “website” remains a source-wording question. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 52, Req 355]

### Frictionless state conclusion

**Normative Requirement plus unresolved omission.** The ACS may select several ARes dispositions, including `Y`, `A`, `N`, `U`, `R`, and `I`, but a frictionless transaction cannot include ACS-initiated Cardholder interaction. The decisioning algorithm itself is outside this specification. Although `I` is an allowed ACS result, the later App 3DS Server disposition branches do not define its downstream handling. [EMV 3DS v2.2.0, section 3.1, pp. 49 and 51-52, Reqs 30, 39-41, 318, and 323]

## 3. App-based challenge preparation and processing - ordered flow

### 3.1 Challenge preparation

1. The common AReq path completes first. If the ACS decides a challenge is necessary, it sets Transaction Status `C`, chooses an acceptable challenge method using at least the specified AReq capability inputs, sets ACS Rendering Type, sets up the ACS-to-SDK secure channel, stores SDK Transaction ID for CReq processing, and stores 3DS Server Transaction ID plus DS Transaction ID for later RReq processing. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 50, Req 32]
2. The ACS formats ARes and returns it ACS -> DS -> 3DS Server. The server evaluates whether the Requestor accepts the requested challenge, using in part the Requestor Challenge Indicator, ACS Challenge Mandated Indicator, and ACS Rendering Type. If accepted, the server passes the necessary ARes values into the Requestor Environment. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, pp. 50-51, Reqs 33-40]
3. The App invokes the SDK `doChallenge` method. The SDK validates the supplied 3DS data elements, completes the ACS-to-SDK secure channel, and establishes a secure link directly to the ACS using the ACS URL received from the 3DS Server and verified during secure-channel completion. [Normative Requirement; Descriptive (SDK method) / Shall] [EMV 3DS v2.2.0, section 3.1, pp. 51-52, Reqs 40 and 42-44]
4. The SDK formats and protects the initial CReq and sends it directly to the ACS. This initial CReq sets up the challenge; it is not an AReq retry and does not traverse the DS or 3DS Server. [Normative Requirement plus Interpretation; Shall] [EMV 3DS v2.2.0, section 3.1, pp. 44 and 52, Figure 3.1, Reqs 45-46]

### 3.2 Challenge processing and UI

1. On the initial CReq, the ACS validates the message, sets Interaction Counter to zero, sets Challenge Completion Indicator to `N`, and obtains the information needed for the selected challenge method and ACS UI Type. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 53, Reqs 47-50]
2. The ACS formats, protects, and sends CRes directly to the SDK. The SDK validates CRes and displays the challenge UI based on ACS UI Type and populated UI data. This is when the challenge UI appears. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 53, Reqs 51-55]
3. Cardholder verification input occurs after UI display: the Cardholder interacts with the SDK UI, for example by entering data and pressing Submit. The SDK then formats, protects, and sends a new CReq directly to the ACS. [Normative Requirement; Descriptive (Cardholder step) / Shall (SDK message handling)] [EMV 3DS v2.2.0, section 3.1, p. 53, Reqs 56-58]
4. The ACS validates that CReq and checks the authentication data entered by the Cardholder. If correct, the ACS increments Interaction Counter, sets Transaction Status `Y`, sets the DS-defined ECI, generates the DS-defined Authentication Value, and sets Challenge Completion Indicator `Y`. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 54, Reqs 60-61]
5. If the entered data is incorrect, the ACS increments the Interaction Counter and compares it with its maximum challenges. At or above the maximum, the ACS sets Transaction Status `N`, Transaction Status Reason `19`, the DS-defined ECI, and Challenge Completion Indicator `Y`. Below the maximum, it prepares repeat challenge information and returns to the CRes step. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 54, Req 61]
6. Each repeat consists of another CRes from ACS to SDK, another SDK-rendered UI interaction, and another CReq from SDK to ACS. These exchanges remain part of the same authentication transaction: the ACS stored the SDK Transaction ID for CReq processing, and Interaction Counter tracks the attempts. Figure 3.1 explicitly places the CReq/CRes exchange inside a loop until challenge completion. [Interpretation; Shall / Figure note] [EMV 3DS v2.2.0, section 3.1, pp. 44, 50, and 53-54, Figure 3.1, Reqs 32, 53, 56, 58, and 61]
7. If the Cardholder abandons during Steps 12-15, the SDK sends a CReq carrying Challenge Cancelation Indicator. If abandonment occurs later or the ACS receives that CReq, the ACS completes the challenge state and carries the appropriate cancellation information into RReq. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, pp. 54-55, Reqs 59-60, 64, and 310]
8. Once authentication reaches an outcome, the ACS formats RReq, establishes the result link to the DS, and sends RReq. The DS validates it and forwards it to the 3DS Server using the 3DS Server URL stored from AReq. The 3DS Server validates RReq, returns RRes to the DS, and the DS validates, logs, and returns RRes to the ACS. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, pp. 54-56, Reqs 62-75]
9. After the RReq/RRes result-notification exchange, the ACS formats, protects, and sends the final CRes to the SDK. The SDK validates it, conveys the appropriate response to the App, and the App displays the result to the Cardholder. Req 76 defines the final CRes with Table B.5 but invokes Section 6.2.4.4, which protects Table B.4 data elements; the field set is therefore unresolved. [Normative Requirement plus unresolved source inconsistency; Shall / Descriptive final display] [EMV 3DS v2.2.0, section 3.1, p. 56, Reqs 76-79; section 6.2.4.4, p. 144; sections B.4-B.5, pp. 265-266]

## 4. App-based OOB challenge - ordered flow and deltas

1. The OOB flow uses the standard Section 3.1 AReq/ARes path and a Transaction Status `C` challenge. The ACS recognizes that OOB interaction is required. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, section 3.2, p. 57, Figure 3.2]
2. The SDK still sends the initial CReq directly to the ACS. The ACS returns CRes, but its challenge information contains only instructions telling the Cardholder how to perform OOB authentication. [Interpretation; Descriptive (no modal), applying Section 3.1 Reqs 45-53] [EMV 3DS v2.2.0, section 3.1, pp. 52-53, Reqs 45-53] [EMV 3DS v2.2.0, section 3.2, p. 57]
3. Between the initial challenge setup and the later SDK acknowledgement, the ACS initiates an OOB interaction with the Cardholder instead of authenticating through SDK-entered data. The Cardholder authenticates to the ACS or to an Issuer/service provider interacting with the ACS. OOB communication and the authentication method are outside the specification; the push-notification/banking-app path is only an example. [Scheme or Vendor Gap; Descriptive (explicitly out of scope)] [EMV 3DS v2.2.0, section 3.2, p. 57, Figure 3.2]
4. When the Cardholder returns from an OOB app on the same device, no further Cardholder action is required in the Requestor App: the SDK automatically posts CReq when the App comes to the foreground. That CReq is only an acknowledgement that the Cardholder may have performed OOB authentication; it does not carry the OOB authentication result. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, section 3.2, pp. 57-58]
5. At the challenge decision step, the ACS obtains success or failure from the OOB interaction, not from CReq. The ACS must have access to that OOB result before result notification begins. If the Cardholder did not authenticate, the ACS can send another CRes with updated instructions, thereby repeating CRes/CReq within the same challenge transaction. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, section 3.2, p. 58, applying section 3.1, p. 54, Req 61]
6. After the ACS has the OOB outcome, the standard RReq/RRes route and final CRes route apply: the server-side result is notified through ACS -> DS -> 3DS Server -> DS -> ACS, then final CRes completes the SDK-side challenge. [Interpretation; Shall through incorporated Section 3.1 requirements] [EMV 3DS v2.2.0, section 3.1, pp. 54-56, Reqs 62-79] [EMV 3DS v2.2.0, section 3.2, pp. 57-58, Figure 3.2]

### 6.2 State transitions

| Event | ACS state transition | Requirement level and citation |
|---|---|---|
| Frictionless decision | AReq disposition can become `Y`, `A`, `N`, `U`, `R`, or `I`; no ACS-initiated Cardholder interaction is permitted in a frictionless transaction. | [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 49, Reqs 30 and 318] |
| Challenge selected | Transaction Status becomes `C`; ACS Rendering Type is set; SDK Transaction ID and result-routing IDs are stored. | [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 50, Req 32] |
| First CReq received | Interaction Counter becomes `0`; Challenge Completion Indicator becomes `N`. | [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 53, Reqs 47-49] |
| Successful verification | Interaction Counter increments; Transaction Status becomes `Y`; ECI and Authentication Value are produced as defined by the DS; Challenge Completion Indicator becomes `Y`. | [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 54, Req 61] |
| Failed attempt below maximum | Interaction Counter increments; ACS prepares another challenge and returns to the CRes step. | [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, p. 54, Req 61] |

## 8. Multiple CReq/CRes exchanges and the two completion paths

**Interpretation.** Multiple CReq/CRes exchanges are not new AReq transactions. The ACS stores SDK Transaction ID for later CReq processing, initializes one Interaction Counter, increments it for attempts, and loops through CRes -> UI -> CReq until success, maximum failures, cancellation, or another terminal condition. OOB can use the same loop to update instructions and receive another acknowledgement. [Interpretation; Shall / Descriptive] [EMV 3DS v2.2.0, section 3.1, pp. 44, 50, and 53-54, Figure 3.1, Reqs 32, 48, 53, 56, 58, and 61] [EMV 3DS v2.2.0, section 3.2, p. 58]

| Completion artifact | Route and purpose | Cardinality/order | Requirement level and citation |
|---|---|---|---|
| **RReq/RRes result notification** | RReq sends the ACS result through DS to the 3DS Server; RRes acknowledges it back through DS to ACS. This is the server-side result-notification path. | Exactly one RReq must be sent for each ARes with Transaction Status `C` or `D`. In the numbered flow it completes before final CRes. | [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.1, pp. 54-56, Reqs 62-75, especially Req 66] |
| **Final CRes challenge completion** | Final CRes is sent directly from ACS to SDK, is validated by SDK, and causes the SDK to convey the appropriate response to the App. This closes the client-side challenge; it is not RRes and does not acknowledge RReq. Its field set is unresolved because Req 76 names Table B.5 while the invoked Function K subsection names Table B.4. | It follows Steps 18-22 and is the Step 23 continuation of the CReq received at Step 17. | [Normative Requirement plus unresolved source inconsistency; Shall] [EMV 3DS v2.2.0, section 3.1, p. 56, Reqs 76-79; section 6.2.4.4, p. 144; sections B.4-B.5, pp. 265-266] |
