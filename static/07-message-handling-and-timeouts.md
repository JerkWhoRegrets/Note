# Message Handling and Timeouts

## Scope and evidence method

This analysis covers Sections 5.1-5.8 on physical PDF pages 111-123. The PDF is the normative source. Extracted text and Batches 2-6 were used for navigation and flow context; every physical page in the range was rendered and inspected directly. Pages 111-123 contain no figures or tables: the requirements refer to Tables 1.5, A.1, A.2, A.4, B.2, B.6, and B.7 elsewhere in the specification. Table 1.5 on physical page 27 was also inspected directly because Section 5.1.4 makes active-version handling depend on it. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, sections 5.1-5.8, pp. 111-123; section 1.7, p. 27, Table 1.5]

The evidence categories used below are **Normative Requirement**, **Interpretation**, **Issuer ACS Implementation Consideration**, **Scheme or Vendor Dependency**, and **Unresolved**. Source strength is preserved as **Shall**, **Should**, **May**, **Will/Can**, **Note**, or **Descriptive (no modal)**. An implementation consequence is never presented as an EMV 3DS requirement.

## 1. Executive conclusions

1. **The normal transport is secured HTTP POST with a corresponding HTTP response.** All 3DS message requests shall use HTTP POST over the Section 6.1 secured connection; responses shall be sent in the reply to that POST. JSON, JWE, or JWS carriage and the message-specific Content-Type rules apply. [Normative Requirement; Shall] [EMV 3DS v2.2.0, sections 5.1.1-5.1.2, pp. 111-112, Reqs 184-191]
2. **A synchronous response need not be the final authentication outcome.** AReq/ARes is the synchronous authentication HTTP exchange. An ARes with status `C` or `D` leaves transaction state pending; the final challenge or Decoupled result is later carried in a separately initiated RReq, for which RRes is the synchronous acknowledgement. In Browser challenge handling, the initial CReq POST receives ACS HTML, while final CRes is posted later to the Notification URL after RReq/RRes. [Normative Requirement plus Interpretation; Shall] [EMV 3DS v2.2.0, sections 5.1.1 and 5.8.2, pp. 111 and 123, Reqs 189 and 267-270; section 3.3, pp. 68-70, Reqs 124-140; section 3.4, pp. 76-77, Reqs 332-341 and 349-354]
3. **Version support is both platform-wide and transaction-specific.** Table 1.5 marks `2.1.0` and `2.2.0` Active and `2.0.0` Deprecated. Components shall support every active protocol version, process an active supported Message Version under that version's requirements, reject a non-active version with Error Code `102`, and enforce one consistent Message Version throughout a transaction; the 3DS Server sets that version. [Normative Requirement plus table status; Shall / Note] [EMV 3DS v2.2.0, section 1.7, p. 27, Table 1.5; section 5.1.4, p. 112, Reqs 194-195, 311, and 320]
4. **The ACS owns the challenge transaction timers.** It retains `C` ARes state, waits 30 seconds for the initial CReq, and then applies a 10-minute timer to each continuing App CRes or each Browser challenge interface. Initial and App continuation CReqs received after ACS timeout get Error Component `A`, Error Code `402`; Browser late HTML submissions are not assigned an equivalent rule in Sections 5.1-5.8. [Normative Requirement plus Unresolved; Shall / not specified] [EMV 3DS v2.2.0, section 5.5.1, pp. 116-117, Reqs 219-227 and 343-344]
5. **Read timeouts start after connection setup, not while establishing it.** A read timeout starts once the TLS handshake is complete and the full request has been sent. Initial TCP/IP/TLS failures instead follow connection-retry rules. AReq/ARes durations are DS-defined; fixed values in scope are 10 seconds for each SDK CReq read, at least five minutes for the SDK Maximum Timeout, 5 seconds for ACS waiting for RRes from the DS, and 3 seconds for the DS waiting for RRes from the 3DS Server. [Normative Requirement; Shall] [EMV 3DS v2.2.0, sections 5.5.2-5.5.2.3, pp. 117-119, Reqs 228-229, 231-237, 239-245, and 312]
6. **PReq/PRes is capability-cache maintenance, not an authentication result.** It supplies per-card-range ACS/DS protocol-version support and optional 3DS Method URL information for App, Browser, and 3RI use. The Serial Number is a DS-managed delta cursor: omit it for a full load; normally send the latest processed value for changes; replace the DS cache when PRes has no Serial Number. [Normative Requirement plus Interpretation; Shall / Should / Descriptive] [EMV 3DS v2.2.0, section 5.6, pp. 119-121, Reqs 246-251, 303-304, and 385]
7. **Sections 5.1-5.8 do not define a general duplicate-message replay algorithm.** They do require request/response identifier matching, explicitly reject more than one Card Range Data request within one hour, prescribe retry behavior for connection failures, and define late-CReq behavior after ACS timeout. Other duplicate and late-message cases remain implementation or interoperability questions. [Interpretation; Shall for the cited specific rules] [EMV 3DS v2.2.0, sections 5.1.6, 5.5.1, and 5.6, pp. 114, 116, and 120, Reqs 212, 222, 225, and 303]

### 2.2 Supported versions and transaction consistency

Version numbers shall use `major.minor.patch`. A Message Version not Active in Table 1.5 produces an Error Message with the applicable Error Component and Error Code `102`. A version mismatch within one transaction produces the applicable Error Component and Error Code `203`; the source example checks RReq Message Version against AReq. All components shall support all active protocol versions and process an active supported Message Version under the specified version's requirements. The 3DS Server sets the Message Version used by all components for the transaction. [Normative Requirement; Shall / Note] [EMV 3DS v2.2.0, section 5.1.4, p. 112, Reqs 194-195, 311, and 320]

Table 1.5's status values are `2.0.0` Deprecated, `2.1.0` Active, and `2.2.0` Active. Therefore the Section 5.1.4 support obligation covers `2.1.0` and `2.2.0` in this edition; `2.0.0` is not Active. [Normative Requirement plus table status; Shall] [EMV 3DS v2.2.0, section 1.7, p. 27, Table 1.5; section 5.1.4, p. 112, Reqs 195 and 311]

### 2.3 Parsing, allowed recipients, and validation

On receipt, a component shall validate the Annex A requirements, transaction context for the Message Type, JSON or JWE/JWS syntax, and whether the Message Type is valid for that component. The accepted inbound types in this scope are: [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.1.5, p. 113, Reqs 196-203]

| Receiving component | Accepted inbound messages | Other types |
|---|---|---|
| 3DS SDK | CRes, Error Message | Shall be treated as an error. [EMV 3DS v2.2.0, section 5.1.5, p. 113, Req 200] |
| 3DS Server | ARes, RReq, PRes, Error Message | Shall be treated as an error. [EMV 3DS v2.2.0, section 5.1.5, p. 113, Req 201] |
| DS | AReq, ARes, RReq, RRes, PReq, Error Message | Shall be treated as an error. [EMV 3DS v2.2.0, section 5.1.5, p. 113, Req 202] |
| ACS | AReq, CReq, RRes, Error Message | Shall be treated as an error. [EMV 3DS v2.2.0, section 5.1.5, p. 113, Req 203] |

Required fields shall be present; Conditional fields shall be present when their source-side conditions are met; all included Required, Conditional, and Optional fields shall meet Table A.1 formatting and length. Unless explicitly allowed, a conditionally optional or optional field sent empty or null produces an Error Message with the applicable Error Component and Error Code `203`. Failed content validation is treated as an error. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.1.6, p. 113, Reqs 204-208 and 309]

Implementations shall not use or configure strictly validating JSON content parsers. A syntactically correct message that meets the Message Type criteria is valid. Extra elements outside the specified Message Type, Device Channel, and Message Category do not invalidate an otherwise valid message. Except for data extensions, the receiver either ignores and drops extra elements, or format-checks them and then drops valid extras or returns an error for malformed extras. Unrecognised non-critical extension name/value pairs shall be silently ignored and passed onward. [Normative Requirement; Shall] [EMV 3DS v2.2.0, sections 5.1.6, pp. 113-114, Reqs 207, 209, and 210]

Response fields defined in Table A.1, including Transaction IDs and Reference Numbers, shall match the corresponding request. A format-validation response shall populate Error Detail with the incorrect element name or names. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.1.6, p. 114, Reqs 212-213]

### 2.4 Partial outage, availability, and error-code behavior

When a component detects a system failure, it shall stop accepting requests until corrected and shall send outstanding requests an Error Message with the applicable Error Component and Error Code `403` or `404`. The section does not state how to choose between those two codes. [Normative Requirement plus Unresolved; Shall / selection not specified] [EMV 3DS v2.2.0, section 5.2, p. 115, Req 215]

High availability is recommended. A component's message routing or load balancing should not rely on another component, and multiple stored routing URLs should not be the only high-availability solution. Detailed high-availability practices are outside scope. [Normative Recommendation; Should / May / Note] [EMV 3DS v2.2.0, section 5.3, p. 115]

Components shall accept any Error Code value. If Table A.4 has no exact condition match, a reasonably close Error Code shall be used. For Error Codes `201`, `203`, `204`, and `304`, the detecting component shall name the erroneous element or elements in Error Detail. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.4, p. 115, Reqs 216-218]

## 4. Duplicate, retry, state, and correlation rules

### 4.1 Explicit rules and evidence boundary

- **Request/response matching is mandatory.** Transaction IDs, Reference Numbers, and other Table A.1 response elements shall match the corresponding request. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.1.6, p. 114, Req 212]
- **PReq has an explicit rate/duplicate rule.** More than one request for Card Range Data within one hour causes the DS to return Error Component `D`, Error Code `103`. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.6, p. 120, Req 303]
- **Late CReq has an explicit terminal response.** A CReq received after the initial 30-second ACS timeout produces Error Component `A`, Error Code `402` to the SDK or Browser Requestor; an App CReq received after the 10-minute continuation timeout produces the same error to the SDK. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.5.1, p. 116, Reqs 222 and 225]
- **Connection retry is not a general message replay rule.** The prescribed retries follow failure to complete initial TCP/IP/TLS connection establishment. Sections 5.1-5.8 do not say that a receiver shall replay a cached response when a fully delivered AReq, CReq, RReq, or PReq is received again. [Interpretation; evidence boundary] [EMV 3DS v2.2.0, sections 5.5.2.1-5.5.2.3 and 5.6, pp. 117-120, Reqs 229, 233, 236, 240, 243, and 248-249]
- **Result-message cardinality still applies.** The flow requirements require one RReq for each `C` or `D` ARes; transport retry should not be interpreted as permission to create multiple semantic results. [Normative Requirement plus Implementation Interpretation; Shall] [EMV 3DS v2.2.0, section 3.1, p. 55, Req 66; section 3.3, p. 68, Req 128; section 3.4, p. 76, Req 352]

## 6. PReq/PRes processing and version/range information

PReq/PRes lets each 3DS Server maintain DS-specific card-range capability data: supported Protocol Version Numbers for available ACSs and the DS, and any 3DS Method URL. The information can be used in App, Browser, and 3RI flows. It informs version/range capability and Method discovery; it does not replace the requirement that the transaction Message Version be Active, supported, and consistent. [Normative Requirement plus Interpretation; Shall] [EMV 3DS v2.2.0, sections 5.1.4 and 5.6, pp. 112 and 119, Reqs 195, 311, and 320]

The cache cycle is: [Normative Requirement plus Descriptive; Shall / Should] [EMV 3DS v2.2.0, section 5.6, pp. 119-121, Reqs 246-251, 303-304, and 385]

1. For first load, flushed cache, or a DS without partial updates, omit Serial Number so the DS returns the full participating card-range list. Otherwise the 3DS Server **should** include the Serial Number from its most recently processed PRes so the DS can return only later changes. An invalid or too-old Serial Number should produce Error Code `307`; Req 303 makes that DS response an Error Message with Error Component `D`. [Normative Requirement plus Descriptive; Should / Shall] [EMV 3DS v2.2.0, section 5.6, pp. 119-120, Req 303]
2. If Serial Number is unchanged, Card Range Data should be absent while Serial Number should remain present. If PReq has no Serial Number, or the DS does not support partial update, PRes shall contain all Card Range Data using only Action Indicator `A`. [Normative Requirement plus Descriptive; Should / Shall] [EMV 3DS v2.2.0, section 5.6, pp. 119-120, Req 250]
3. The 3DS Server shall call each registered DS at least once every 24 hours and no more than once per hour when no PRes-processing errors are found, using the Section 6.1.2.1 secure link. A second Card Range Data request within one hour receives Error Component `D`, Error Code `103`. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.6, pp. 119-120, Reqs 246-247 and 303]
4. The DS validates PReq: malformed present data gives `D/203`, missing required data gives `D/201`, invalid Serial Number gives `D/307`, and more than one request in one hour gives `D/103`. It returns only participating, registered card account ranges. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.6, p. 120, Reqs 251 and 303]
5. The 3DS Server validates PRes: malformed present data gives `S/203` and missing required data gives `S/201`. It applies each Card Range Data entry according to Action Indicator; PRes without Serial Number replaces all existing Card Range Data for that DS. If an error is found in Card Range Data, the server resubmits PReq without Serial Number. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.6, pp. 120-121, Reqs 304 and 385]

No PRes read-timeout duration or late-PRes rule appears in Section 5.6. The general HTTP-response requirement and PReq connection-retry rules apply, but handling a response that arrives after local cache-refresh abandonment is not specified here. [Unresolved; evidence boundary] [EMV 3DS v2.2.0, sections 5.1.1 and 5.6, pp. 111 and 119-121, Reqs 189 and 246-251]

## 7. App/SDK-based message handling

The 3DS SDK shall conform to the separate EMV 3-D Secure SDK Specification requirements and APIs. In this Core specification it supplies SDK data through the Requestor Environment toward the 3DS Server/DS/ACS, provides App challenge UI, and handles CReq/CRes. App CReq/CRes is direct communication between the Consumer Device via the 3DS Client and the ACS. [Normative Requirement plus Descriptive; Shall] [EMV 3DS v2.2.0, section 5.7, p. 121]

The SDK builds CReq from ARes data supplied through the Requestor App. It shall verify the JWS signature in ACS Signed Content using the pre-installed public key of the DS called for the transaction, then generate CReq JWE objects from the SDK ephemeral key and ACS Ephemeral key. On CRes it displays the UI and sends the Cardholder result in another CReq; several interactions may occur. [Normative Requirement plus Note; Shall] [EMV 3DS v2.2.0, section 5.7.1, p. 121, Reqs 253-254]

The fixed SDK timing model is two-layered: every CReq has a 10-second CRes read timeout, while the whole challenge has a configured SDK Maximum Timeout of at least five minutes starting with the first CReq. These are separate from the ACS's 30-second initial-CReq timer and 10-minute continuation timer. [Normative Requirement plus Interpretation; Shall] [EMV 3DS v2.2.0, sections 5.5.1 and 5.5.2.2, pp. 116 and 118, Reqs 220-225, 237, 239, and 312]

## 8. Browser-based message handling

### 8.1 3DS Method

ACS use of the 3DS Method, and ACS inclusion of a Method URL/account ranges in the DS, is optional. When cached PRes data for the card range contains a 3DS Method URL, the Requestor shall invoke it before the AReq for the same transaction; Requestor timing within that boundary is chosen to optimise user experience. If no Method URL exists, the Requestor notifies the 3DS Server to set Method Completion Indicator `U`. [Normative Requirement; Shall / Optional / Note] [EMV 3DS v2.2.0, section 5.8.1, p. 122, Reqs 255-258]

The Requestor sends initial Base64url-encoded 3DS Method Data containing the same 3DS Server Transaction ID later used in AReq and the Method Notification URL, in `threeDSMethodData` through a hidden iframe POST. The ACS interacts with the Browser, stores applicable values under that ID for the matching AReq, and causes the recalled ID to be posted to the Method Notification URL. Req 263 does not repeat Req 260's JSON/Base64url construction for the completion value; Annex A.5.3 Example 2 demonstrates it. The 3DS Server sets completion `Y` on notification or `N` if the Method does not complete within 10 seconds. ACS action during Method execution **should** not affect user experience. [Normative Requirement plus Interpretation / Unresolved completion wording; Shall / Should] [EMV 3DS v2.2.0, section 5.8.1, pp. 122-123, Reqs 259-264 and 315; section A.5.3, pp. 224-225, Table A.2]

### 8.2 Browser challenge

The Requestor shall select a standardized iframe size, use server-authenticated TLS, create the challenge window, generate CReq, and POST it through the iframe to the ACS URL from ARes. CReq carries the selected Challenge Window Size. The Requestor shall provide a non-JavaScript redirect fallback. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 5.8.2, p. 123, Reqs 265-268 and 324]

The ACS shall receive CReq and synchronously respond with HTML that renders in the iframe. Several Cardholder interactions may follow, but they remain browser HTML traffic within the same protocol challenge. After completion, the ACS generates RReq; after the corresponding RRes, it generates CRes and invokes the browser to POST CRes to the Notification URL. The Requestor then refreshes the parent page and removes the iframe. [Normative Requirement plus Interpretation; Shall / Note] [EMV 3DS v2.2.0, section 5.8.2, p. 123, Reqs 269-270; sections 2.4.3-2.4.4, pp. 34-35]

## 9. ACS idempotency, persistence, locking, and transaction state

The entries below are **Issuer ACS Implementation Considerations**, except where an express normative anchor is quoted. The specification does not mandate a database, lock manager, queue, cache product, or internal issuer API.

| Concern | Normative anchor | Issuer ACS Implementation Consideration |
|---|---|---|
| Durable pending state | ACS shall maintain a `C` ARes transaction so corresponding CReq and timeouts can be processed; flows also require storing named IDs for later CReq/RReq processing. [EMV 3DS v2.2.0, section 5.5.1, p. 116, Req 219; section 3.1, p. 50, Req 32] | Persist enough state to survive process/node failure through the initial-CReq deadline, continuing challenge, RReq/RRes delivery, and final CRes path. At minimum model selected Message Version, transaction IDs, current phase, timer deadlines, terminal outcome, and required routing/cryptographic state. Exact schema and retention are implementation decisions. |
| Timeout/message race | Expiry sends a terminal RReq and, for initial/App continuation timeout, clears the ephemeral key; late CReq then gets `A/402`. [EMV 3DS v2.2.0, section 5.5.1, p. 116, Reqs 221-225] | Serialize or atomically compare-and-set the race between timeout worker and inbound CReq/Browser submission. Only one path should win the terminal transition; locking technology is not prescribed. |
| One semantic result | One RReq is required per `C` or `D` ARes, while ACS connection retries can repeat until delivery. [EMV 3DS v2.2.0, section 3.1, p. 55, Req 66; section 5.5.2.3, p. 118, Req 240] | Reuse the same logical result state across transport attempts. Do not create a fresh authentication decision or second semantic RReq merely because connection outcome is uncertain. The precise receiver-side duplicate replay behavior is not standardized in Sections 5.1-5.8. |
| Idempotent response application | Response Transaction IDs and Reference Numbers shall match the request; Message Version remains consistent. [EMV 3DS v2.2.0, sections 5.1.4 and 5.1.6, pp. 112 and 114, Reqs 212 and 320] | Validate correlation and current phase before mutating state. Record terminal completion so a duplicate or late response cannot reopen a completed transaction. Whether to return a stored response for a duplicate request is not specified. |
| Ephemeral-key lifecycle | Initial/App ACS timeout shall clear the ephemeral key used for that CReq/CRes exchange. [EMV 3DS v2.2.0, section 5.5.1, p. 116, Reqs 221 and 224] | Couple key deletion to the same atomic terminal transition as timeout result creation. Prevent a racing late CReq from using key material after timeout. Key storage design is governed by Chapter 6 and implementation architecture, not inferred here. |
| 3DS Method correlation | ACS shall store Method values with the 3DS Server Transaction ID for the later AReq with the same ID. [EMV 3DS v2.2.0, section 5.8.1, pp. 122-123, Reqs 262-263] | Define an expiry, duplicate-callback policy, and atomic consume/update behavior for pre-AReq Method state. The 10-second timer does not state whether a later callback changes `N` to `Y`. |
| Browser challenge state | Each sent interface starts a 10-minute timer; final CRes follows RReq/RRes. [EMV 3DS v2.2.0, sections 5.5.1 and 5.8.2, pp. 116-117 and 123, Reqs 226-227, 343-344, and 269-270] | Persist interaction counter, current interface generation, authentication state, deadline, and final-return state. Use atomic progression so duplicate form submissions or timeout cannot produce conflicting outcomes. Browser form idempotency itself is not standardized. |
| PRes cache consistency | PRes entries are applied by Action Indicator; no Serial Number means replace the DS cache; Card Range Data error triggers a full resubmission. [EMV 3DS v2.2.0, section 5.6, pp. 120-121, Req 385] | On the 3DS Server side, apply range mutations and the new Serial Number atomically, and isolate each DS cache. This is an implementation consideration, not an ACS duty or prescribed storage model. |

## 10. Unresolved and implementation-dependent items

1. **RReq connection retry with status `U`.** Req 240 says that after the second ACS-to-DS connection failure the ACS will retry every 10 seconds until the message is delivered "with Transaction Status = U." It does not say whether an already determined `Y`, `N`, or other result must be replaced by `U`, or whether `U` describes a separately formatted retry result. Authoritative clarification is required before changing a completed authentication outcome solely because result delivery failed. [Unresolved source wording] [EMV 3DS v2.2.0, section 5.5.2.3, p. 118, Req 240]
2. **3DS Method timer start and late notification.** Req 315 gives a 10-second completion threshold but does not state its precise start event or whether a callback after the server has set `N` may change the indicator, especially after AReq submission. [Unresolved] [EMV 3DS v2.2.0, section 5.8.1, pp. 122-123, Reqs 257, 261, 263, and 315]
3. **No general duplicate/replay contract.** Apart from PReq rate limiting and late-CReq errors, Sections 5.1-5.8 do not define duplicate detection keys, cached-response replay, or behavior after uncertain full-message delivery. Cross-vendor interoperability needs applicable DS/SDK rules and local idempotency policy. [Unresolved / Scheme or Vendor Dependency] [EMV 3DS v2.2.0, sections 5.1.6, 5.5, and 5.6, pp. 114-120, Reqs 212, 222, 225, 229, 233, 236, 240, 243, and 303]
4. **Browser late submissions.** The Browser challenge completes with RReq and CRes after the 10-minute interface timeout, but no error code or response is assigned to a later HTML form submission. [Unresolved / Issuer ACS Implementation Consideration] [EMV 3DS v2.2.0, section 5.5.1, pp. 116-117, Reqs 226-227 and 343-344]
5. **DS-defined AReq/ARes values.** The actual 3DS Server-to-DS and DS-to-ACS read durations are set by each DS and may vary per DS; this Core specification supplies no numeric value. [Scheme or Vendor Dependency] [EMV 3DS v2.2.0, section 5.5.2.1, pp. 117-118, Reqs 228, 231, and 234]
6. **PRes timeout and late response.** Section 5.6 defines connection retry and refresh cadence but no PRes read-timeout duration, uncertain-delivery duplicate rule, or late-PRes behavior. [Unresolved] [EMV 3DS v2.2.0, section 5.6, pp. 119-121, Reqs 246-251]
7. **Partial-outage code selection.** Req 215 permits Error Code `403` or `404` for outstanding requests but supplies no selection criterion in Sections 5.1-5.8. [Unresolved / Scheme or Vendor Dependency] [EMV 3DS v2.2.0, section 5.2, p. 115, Req 215]
