# Browser and 3RI User Interface

## Scope and evidence method

This analysis covers Sections 4.3 and 4.4 on physical PDF pages 102-110. The PDF is the normative source. Extracted text was used for navigation and requirement discovery; every physical page in the range and every UI example (Figures 4.19-4.23) was inspected directly. No table appears on pages 102-110, and physical page 110 is intentionally blank. The relevant supplemental browser-window, timeout, POST, and message-format material on physical pages 116-118, 123, 165, 195, 226, and 264-266 was also checked visually. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, sections 4.3-4.4, pp. 102-110, Figures 4.19-4.23; sections 5.5.1-5.5.2.2, pp. 116-118; section 5.8.2, p. 123; section A.4, pp. 165 and 195; section A.5.4, p. 226, Table A.3; sections B.3-B.5, pp. 264-266, Tables B.3-B.5]

Physical page 102 begins with the end of App HTML handling. Req 171 and its submit pass-through text belong to Section 4.2.7.3, not to the Browser UI in Section 4.3. They are addressed below only to prevent App web-view submission from being confused with Browser challenge submission. [Interpretation; source-layout boundary] [EMV 3DS v2.2.0, section 4.2.7.3, p. 102, Req 171]

The evidence categories used below are **Normative Requirement**, **Interpretation**, **Issuer ACS Implementation Consideration**, **Scheme or Vendor Gap**, and **Unresolved**. Requirement levels are stated as **Shall**, **Should**, **May**, **Note**, or **Descriptive (no modal)**. Figure content is treated as an example unless a requirement expressly makes it mandatory.

## 1. Executive conclusions

1. **The Browser challenge body is ACS-provided HTML in an iframe, placed either as a Lightbox or Inline experience.** The 3DS Requestor or 3DS Integrator chooses the iframe size and website placement; the ACS formats the HTML for the Consumer Device and applicable window size. The Browser UI does not require the App-style Requestor Header zone. [Normative Requirement plus Descriptive; Shall / Descriptive] [EMV 3DS v2.2.0, sections 4.3-4.3.3, pp. 102-108, Reqs 177 and 380-384, Figures 4.19-4.23; section 5.8.2, p. 123, Reqs 265-269]
2. **Lightbox and Inline are browser placement patterns, not `acsUiType` values.** The standardized `acsUiType` values Text, Single Select, Multi Select, OOB, and HTML are defined for the App device channel and for UI rendered by the 3DS SDK. Browser examples show multi-select and text/question experiences, but Sections 4.3-4.4 do not define a separate browser UI-type enumeration or require every App ACS UI Type in Browser. [Interpretation; table boundary / sample figures] [EMV 3DS v2.2.0, section 4.3, pp. 102-108, Figures 4.19 and 4.22-4.23; section A.4, p. 165; section B.4, pp. 265-266]
3. **One Browser CReq and one final Browser CRes can coexist with several browser HTTP interactions.** The initial HTTP POST carries the Base64url-encoded CReq in form field `creq`; ACS HTML responses, resource requests, redirects, and Cardholder form submissions are separate HTTP traffic and are not additional EMV 3DS CReq/CRes messages. After the RReq/RRes result exchange, the browser sends the Base64url-encoded final CRes in form field `cres` to the Notification URL. [Normative Requirement plus Interpretation; Shall / Descriptive] [EMV 3DS v2.2.0, sections 2.4.3-2.4.4, pp. 34-35; section 3.3, pp. 66-70, Reqs 117-140; section 5.8.2, p. 123, Reqs 267-270; section A.5.4, p. 226, Table A.3]
4. **The standardized browser boundary does not standardize the Issuer's authentication application.** EMV 3DS specifies iframe sizing, browser POST envelopes, secure transport, UI zones, progress behavior, limited controls, result ordering, and window closure. The authentication method, issuer service APIs, HTML application structure, session mechanism, detailed content, validation logic below the stated challenge-result rules, translation workflow, and most accessibility/masking behavior remain ACS, issuer, DS, vendor, or regulatory implementation matters. [Interpretation; implementation boundary] [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 120-123 and 307; sections 4.3-4.4, pp. 102-109, Reqs 172-183 and 380-384]
5. **A 3RI transaction may have no 3DS Client UI at all.** In the first Section 4.4 case the Cardholder is absent, so no UI is presented. In a Decoupled 3RI case, the ACS-provided authentication UI is outside EMV 3DS; the Requestor may show processing and convey Cardholder Information Text, including verbally for the cited MOTO scenario. This matches the server-side 3RI topology, which has no Browser or SDK lane. [Interpretation; Descriptive / May] [EMV 3DS v2.2.0, sections 3.4 and 4.4, pp. 71 and 109, Figure 3.4]

## 2. Browser templates, dimensions, content, and controls

### 2.1 Zones and placement

The common UI template has Header, Branding, Challenge/Processing, and Information zones, but the Browser UI omits the App Header zone because the UI appears inside the browser window. The Browser challenge HTML must use form elements in the applicable remaining zones. The Requestor or Integrator provides the iframe dimensions and chooses where it appears in the Requestor website. [Normative Requirement plus Descriptive; Shall] [EMV 3DS v2.2.0, sections 4.1 and 4.3-4.3.2.1, pp. 79-81 and 102-103, Figure 4.1, Reqs 359 and 380]

The two depicted browser placements are:

- **Lightbox:** the merchant page is visually de-emphasized and the processing or challenge panel is centered over it. Figures 4.20 and 4.22 are examples, not a requirement to dim the page in a particular way. [Sample figure / Descriptive] [EMV 3DS v2.2.0, section 4.3.3, pp. 105 and 107, Figures 4.20 and 4.22]
- **Inline:** the iframe occupies a chosen region of the merchant page without a modal overlay. Figures 4.21 and 4.23 are examples, not a prescribed merchant layout. [Sample figure / Descriptive] [EMV 3DS v2.2.0, section 4.3.3, pp. 106 and 108, Figures 4.21 and 4.23]

### 2.2 Challenge-window dimensions and rendering

The 3DS Requestor selects one of the standardized `challengeWindowSize` values for the iframe and includes it in the Browser CReq. The fixed values are `01` = 250 x 400, `02` = 390 x 400, `03` = 500 x 600, `04` = 600 x 400, and `05` = full screen; fixed dimensions are width x height in pixels. The field is required for Browser payment and non-payment CReq messages. [Normative Requirement plus table definition; Shall / Table] [EMV 3DS v2.2.0, section 5.8.2, p. 123, Reqs 265 and 268; section A.4, p. 195, `challengeWindowSize`; section B.3, p. 264, Table B.3]

The ACS must maintain HTML versions corresponding to the supported Challenge Window Size values, and the field definition requires ACS content to render appropriately within the selected window. The ACS also owns formatting the HTML for the Consumer Device. Req 177's literal AReq/CRes wording conflicts with the Browser CReq/HTML path established elsewhere; that source issue is preserved in the unresolved section rather than silently rewritten. [Normative Requirement plus Unresolved; Shall] [EMV 3DS v2.2.0, sections 4.3.1.2 and 4.3.2, p. 103, Req 177; section 5.8.2, p. 123, Reqs 268-269; section A.4, p. 195]

No requirement on pages 102-110 mandates responsive breakpoints, automatic resizing after load, scrolling behavior, device orientation handling, or a safe-area policy. Full screen is a standardized size choice, but Lightbox versus Inline placement remains a Requestor/Integrator decision. [Interpretation; evidence boundary] [EMV 3DS v2.2.0, sections 4.3-4.3.3, pp. 102-108; section A.4, p. 195]

### 2.3 Processing screens

For the AReq/ARes cycle, the 3DS Requestor website must create and display a processing screen that conveys progress, include the DS logo in the center unless specifically told not to, include no other design element, and display it for at least two seconds. A progress bar or spinning wheel is an example of the required Processing Graphic. Figures 4.20 and 4.21 show Lightbox and Inline examples. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 4.3.1.1, p. 102, Reqs 172-176; section 4.3.3, pp. 105-106, Figures 4.20-4.21]

For ACS-side processing during the browser challenge HTML exchange, the ACS must create a processing screen, show a graphical progress element in the Challenge/Processing zone, include no other design element, and display it for at least one second. During the challenge flow outside that processing screen, the ACS must include the DS logo unless specifically told not to. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 4.3.1.2, p. 103, Reqs 178-182]

### 2.4 Challenge content and controls

The Browser challenge is Issuer-specific ACS HTML that follows the template zones. Figure 4.19 shows visual consistency with App HTML through a multi-select question, issuer and payment-system logos, a Next control, Cancel, and expandable information. Figures 4.22-4.23 show a text/question experience with an image, entry field, Next, Cancel, and expandable help. These are examples of content and format; they do not make security questions, images, the exact labels, colours, or control placement mandatory. [Interpretation; sample figures] [EMV 3DS v2.2.0, section 4.3.3, pp. 103-104 and 107-108, Figures 4.19 and 4.22-4.23]

If the ACS uses the optional information elements, it must provide Expandable Information Label and Why Information Label as expandable graphical controls in the Information zone. Their associated text is displayed only when the Cardholder selects the corresponding label. No EMV 3DS message is generated merely by opening or closing one of these controls. [Normative Requirement plus Interpretation; Shall] [EMV 3DS v2.2.0, section 4.3.2.1, p. 103, Reqs 381-384]

The figures show Cancel, and the all-channel template on page 81 shows Resend Code, but Section 4.3 does not define a browser-specific Cancel or Resend form schema. Browser Cardholder data and actions are submitted to the ACS as HTML traffic. If the Cardholder abandons the browser challenge during Steps 12-14, the ACS must report the appropriate Challenge Cancelation Indicator in RReq; an App-style follow-up CReq with `challengeCancel` or `resendChallenge` must not be inferred for Browser because the browser challenge uses only one CReq. [Normative Requirement plus Interpretation; Shall / evidence boundary] [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 122 and 126; sections 4.1 and 4.3.3, pp. 81 and 104-108, Figures 4.2 and 4.19-4.23; section B.3, p. 264]

## 3. Browser form submission and protocol-message carriage

### 3.1 Initial CReq POST

The CReq is Base64url-encoded and carried in an HTTP POST through the browser iframe to the ACS URL from ARes. The form field is named `creq`. It may also contain `threeDSSessionData`, which the ACS must preserve unchanged for the final return; it may be absent if the Requestor can correlate the final POST without it. The browser-to-ACS link uses server-authenticated TLS. The source is inconsistent about the internal author: Req 117 assigns CReq formatting, encoding, form construction, and POST initiation to the 3DS Server, while Req 267 assigns generation of the CReq, iframe, and POST to the 3DS Requestor. [Normative Requirement plus unresolved source inconsistency; Shall / Optional] [EMV 3DS v2.2.0, section 3.3, pp. 66-67, Req 117; section 5.8.2, p. 123, Reqs 266-268; section A.5.4, p. 226, Table A.3]

The CReq is a JSON EMV 3DS protocol message inside a form field; it is not the HTTP POST itself. For Browser, `challengeWindowSize` is a required CReq field. Fields listed in the generic CReq table for App interaction, such as `challengeDataEntry`, `challengeHTMLDataEntry`, `resendChallenge`, and SDK counters, must not be assumed to create repeated Browser CReq messages. [Interpretation; table boundary] [EMV 3DS v2.2.0, sections 2.4.3 and 5.8.2, pp. 34 and 123, Reqs 267-268; sections A.4 and B.3, pp. 195 and 264]

### 3.2 ACS HTML and Cardholder submissions

After validating the one Browser CReq, the ACS responds with HTML that renders the challenge in the iframe. The Cardholder enters the requested data and the browser submits it to the ACS. The ACS may return another challenge interface when the entry is incorrect and the maximum has not been reached; the specification says the HTML exchange repeats until the ACS determines an outcome. Each response may cause separate browser HTTP requests, form posts, navigation, JavaScript execution, and authentication-related resource loads. Those requests are not additional CReq or CRes messages. [Normative Requirement plus Interpretation; Shall / Descriptive] [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 119-123 and 307; section 5.8.2, p. 123, Req 269]

This differs from the App HTML spillover at the top of page 102. In App HTML, a web view returns a GET parameter string or POST form data to the SDK, and the SDK must pass it unchanged in CReq `challengeHTMLDataEntry`; the SDK then transmits that CReq to the ACS. Browser challenge forms instead submit through the browser directly to the ACS within the HTML exchange. [Normative Requirement plus Interpretation; Shall] [EMV 3DS v2.2.0, section 4.2.7.3, p. 102, Req 171; section 3.3, pp. 67-68, Reqs 122-123]

### 3.3 Final CRes POST and completion

After the ACS determines the result, it sends RReq through the DS and receives RRes before creating the final CRes. The final CRes is Base64url-encoded and browser-posted to the Notification URL supplied in AReq, using form field `cres`; optional `threeDSSessionData` is returned unchanged. Req 270 requires the 3DS Requestor to refresh the parent page and remove the iframe, but the source does not consistently identify whether the Notification URL terminates at the 3DS Requestor Environment or 3DS Server. RReq/RRes is the server-side result-notification exchange; the browser CRes POST is the UI-return exchange. [Normative Requirement plus unresolved source inconsistency; Shall] [EMV 3DS v2.2.0, section 3.3, pp. 68-70, Reqs 124-140; sections 5.5.1, 5.8.2, and 5.9.6, pp. 117, 123, and 127-128, Reqs 344 and 270; section A.4, p. 206; section A.5.4, p. 226, Table A.3]

Table A.3 says the posted `cres` contains the entire CRes as defined in Table B.4, while Req 138 and Table B.5 identify the completion message as the final CRes. The implementation impact of that source mismatch is unresolved; the analysis does not merge the Table B.4 UI payload with the Table B.5 final payload. [Unresolved source inconsistency] [EMV 3DS v2.2.0, section 3.3, p. 70, Req 138; section A.5.4, p. 226, Table A.3; sections B.4-B.5, pp. 265-266]

### 3.4 Protocol messages versus browser HTTP exchanges

| Layer | Examples | Cardinality and meaning | Citation |
|---|---|---|---|
| EMV 3DS protocol | Browser CReq, final Browser CRes, RReq/RRes | One CReq and one CRes per Browser challenge; exactly one RReq for each `C` or `D` ARes. These are defined JSON messages with transaction semantics. | [EMV 3DS v2.2.0, sections 2.4.3-2.4.6, pp. 34-35; section 3.3, pp. 67-70, Reqs 119-140] |
| HTTP envelope carrying protocol | POST field `creq` to ACS; POST field `cres` to Notification URL; optional `threeDSSessionData` | Each HTTP POST carries a Base64url protocol payload. The HTTP request is transport, not another protocol message. | [EMV 3DS v2.2.0, section 5.8.2, p. 123, Reqs 267-270; section A.5.4, p. 226, Table A.3] |
| Browser challenge application traffic | ACS HTML response, Cardholder form submissions, redirects, JavaScript, necessary resource requests | There may be several interactions. They remain inside the ACS-managed HTML exchange and do not change CReq/CRes cardinality. | [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 122-123 and 307; section 5.8.2, p. 123, Req 269] |
| Server-side result exchange | RReq ACS -> DS -> 3DS Server; RRes return | Delivers and acknowledges the authentication result before the final browser CRes return. It is not a browser form submission. | [EMV 3DS v2.2.0, section 3.3, pp. 68-70, Reqs 124-137] |

The source does not require one HTTP request, TCP connection, or TLS connection to remain open throughout Cardholder think time and repeated HTML interactions. It specifies a TLS-protected logical path and distinct POST actions. Connection reuse, cookie/session design, and browser storage are implementation matters. [Implementation inference; not a protocol requirement] [EMV 3DS v2.2.0, section 3.3, pp. 66-70, Reqs 117-140; section A.5.4, p. 226, Table A.3]

### Security-sensitive browser behavior stated by the source

- The browser challenge POST must use server-authenticated TLS. The ACS must use a commercial CA supported by major browsers. These requirements do not establish certificate pinning, mutual TLS to the browser, or a particular browser trust-store policy. [Normative Requirement plus evidence boundary; Shall] [EMV 3DS v2.2.0, sections 4.3.1.2 and 5.8.2, pp. 103 and 123, Reqs 183 and 266]
- A Requestor using JavaScript redirection must provide a fallback for environments without JavaScript. JavaScript is therefore permitted, not mandatory. [Normative Requirement; Shall] [EMV 3DS v2.2.0, sections 3.3 and 5.8.2, pp. 67 and 123, Req 324]
- ACS redirects may be used only for authentication purposes and must not take the Cardholder to registration or marketing pages. External resources are limited to those needed to improve the authentication experience and security, such as logos. This Browser rule is not the stricter App HTML rule that requires every resource to be embedded. [Normative Requirement plus comparison; Shall] [EMV 3DS v2.2.0, section 3.3, p. 67, Req 307; section 4.2.7, p. 101, Reqs 160-170]
- Optional `threeDSSessionData` is opaque Requestor data that the ACS preserves unchanged. Its availability does not define cookies, SameSite attributes, CSRF tokens, origin policy, CSP, iframe sandboxing, storage lifetime, or server-session design. Those controls remain implementation decisions and must not be attributed to Sections 4.3-4.4. [Normative table definition plus evidence boundary] [EMV 3DS v2.2.0, section A.5.4, p. 226, Table A.3]

## 7. 3RI user-interface considerations

Section 4.4 describes two UI cases without adding numbered requirements:

1. **Cardholder-absent 3RI, mainly recurrent account/payment-form validation.** The Cardholder is not present, so no UI is presented. This is not a hidden or omitted Browser challenge; it is a server-side 3RI transaction. [Descriptive (no modal)] [EMV 3DS v2.2.0, section 4.4, p. 109]
2. **3RI with requested Decoupled Authentication, such as the cited MOTO example.** The ACS's authentication UI is outside EMV 3DS. The Requestor can show a processing screen during AReq/ARes and convey ACS-provided Cardholder Information Text. For a land-line or feature-phone MOTO transaction, a customer-service representative can convey that text verbally. [Descriptive / May] [EMV 3DS v2.2.0, section 4.4, p. 109]

The 3RI topology contains 3DS Requestor, 3DS Server, DS, ACS, and an optional external Authentication Service, but no Browser or SDK/3DS Client lane. Therefore the EMV 3DS exchange can complete or continue Decoupled without a 3DS Client UI. Any issuer authentication screen, phone script, push experience, or other Cardholder interaction belongs to the external Decoupled method; the ACS still owns the authentication decision and later result notification. [Interpretation; topology / out-of-scope method] [EMV 3DS v2.2.0, section 3.4, pp. 71 and 76-77, Figure 3.4, Reqs 330, 332-341, and 349-354; section 4.4, p. 109]

Section 4.4's optional-display wording and verbal MOTO example do not cleanly align with Req 357's mandatory website-display wording when Cardholder Information Text is supplied. That source tension remains unresolved and should not be converted into a universal 3RI website requirement or a universal permission to substitute verbal delivery. [Unresolved source tension] [EMV 3DS v2.2.0, sections 3.4 and 4.4, pp. 76 and 109, Req 357]

## 10. Unresolved and implementation-dependent items

1. **Req 177 names the wrong message locations for Browser sizing.** It says the ACS provides the appropriate size in CRes based on Challenge Window Size supplied in AReq, while Section 5.8.2 and Table A.1 place `challengeWindowSize` in the Browser CReq and have the ACS respond with HTML. Obtain authoritative EMVCo/DS clarification; do not implement an AReq/CRes Browser-size field based only on Req 177. [Unresolved source inconsistency] [EMV 3DS v2.2.0, section 4.3.1.2, p. 103, Req 177; section 5.8.2, p. 123, Reqs 268-269; section A.4, p. 195]
2. **Table A.3 points Browser POST `cres` to Table B.4, while Req 138 points final CRes to Table B.5.** The final browser return follows the Step 21 completion path, but the contradictory table reference needs authoritative clarification before field-level validation is finalized. [Unresolved source inconsistency] [EMV 3DS v2.2.0, section 3.3, p. 70, Req 138; section A.5.4, p. 226, Table A.3; sections B.4-B.5, pp. 265-266]
3. **Req 117 and Req 267 assign browser CReq construction to different actors.** Req 117 requires the 3DS Server to format and encode CReq, construct the form, and initiate the browser POST; Req 267 says the 3DS Requestor generates the CReq, iframe, and POST. The direct Browser -> ACS transport is clear, but internal authorship needs authoritative clarification. [Unresolved source inconsistency] [EMV 3DS v2.2.0, section 3.3, pp. 66-67, Req 117; section 5.8.2, p. 123, Req 267]
4. **The final Browser CRes receiver is not described consistently.** The flow names the 3DS Requestor Environment and Req 270 assigns window closure to the Requestor; the Notification URL is sourced by the 3DS Server, and Section 5.9.6 describes communication with the 3DS Server via the browser. Do not hard-code the terminating component from this specification alone. [Unresolved source inconsistency] [EMV 3DS v2.2.0, section 3.3, pp. 69-70, Reqs 138-140; sections 5.8.2 and 5.9.6, pp. 123 and 127-128, Reqs 269-270; section A.4, p. 206; section A.5.4, p. 226]
5. **3RI Cardholder Information Text delivery is internally inconsistent.** Req 357 says the 3DS Server shall ensure website display, while Section 4.4 says the Requestor can optionally display the text and gives verbal conveyance as a MOTO example. Obtain authoritative clarification for 3RI cases without a website/Cardholder browser. [Unresolved source tension] [EMV 3DS v2.2.0, sections 3.4 and 4.4, pp. 76 and 109, Req 357]
6. **Browser Cancel and Resend semantics beyond the result boundary are not standardized here.** The figures show the controls, and abandonment is represented in RReq, but browser HTML action names, retry confirmation, resend transport, rate limits, and delivery errors remain ACS/issuer implementation decisions. [Issuer ACS Implementation Consideration] [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 122-126; sections 4.1 and 4.3.3, pp. 81 and 104-108, Figures 4.2 and 4.19-4.23]
7. **Accessibility, localization, masking, and browser hardening need external requirements.** Pages 102-110 do not state a conformance standard, locale mechanism, masking algorithm, CSP/cookie/origin policy, or sensitive-input handling policy. Apply relevant DS, scheme, issuer, regulatory, and web-security requirements without attributing them to Sections 4.3-4.4. [Scheme or Vendor Gap / Implementation Decision] [EMV 3DS v2.2.0, sections 4.3-4.4, pp. 102-109]
