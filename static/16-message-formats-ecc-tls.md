# Message Formats, ECC Key Generation, and TLS

## Scope and evidence method

This analysis covers Annex B, Annex C, and Annex D on physical PDF pages 259-274. The preserved PDF is the normative source. The source map, analysis status, App/Browser/3RI flow analyses, message-handling and error analyses, Chapter 6 security analysis, all Annex A data-element analyses, and the relevant extracted text were read for routing, presence, serialization, and security context. Every physical page in the range was rendered and inspected directly; page 274 is intentionally blank. [Interpretation; evidence method] [EMV 3DS v2.2.0, Annexes B-D, pp. 259-274]

The evidence categories used below are **Normative Requirement**, **Interpretation**, **Issuer ACS Implementation Consideration**, **Scheme or Vendor Dependency**, and **Unresolved**. Annexes B-D contain no numbered requirement identifiers, so their direct citations use section, table where applicable, and physical PDF page. Cross-referenced numbered requirements retain their requirement numbers.

## 1. Executive conclusions and evidence boundary

1. **Annex B does not contain example JSON payloads.** Tables B.1-B.10 are field-name indexes by Message Type. They do not show values, JSON member order, a complete instance for any Device Channel or Message Category, HTTP headers, or form markup. Table A.1 remains the source for type, length, value, source, channel/category, and `R`/`C`/`O` presence rules. [Interpretation of annex purpose and table structure] [EMV 3DS v2.2.0, Annex B, pp. 259-270, Tables B.1-B.10; section A.4, pp. 148-222, Table A.1]
2. **The Annex B tables are normative format indexes, not illustrative samples.** Each subsection directs the reader to Table A.1 for default validation, and Sections 5.1.5-5.1.6 require recipients to validate the applicable Annex A requirements and the message-type field set. AReq and ARes additionally permit a specific DS to impose other DS-specific validations or actions. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 5.1.5-5.1.6, pp. 113-114, Reqs 196-210 and 212-213; sections B.1-B.2, pp. 259-263, Tables B.1-B.2]
3. **An Annex B list is a message-level union, not proof that every listed field appears in one payload or on every leg.** Table A.1 decides actual presence by channel, category, condition, and sometimes route leg. For example, App AReq carries `sdkEncData` to the DS, while the DS decrypts it and sends `deviceInfo` to the ACS; the Annex B AReq list contains both names. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, section A.3, p. 147; section A.4, pp. 196 and 212, Table A.1; section B.1, pp. 259-262, Table B.1]
4. **Serialization and transport come from Chapters 5-6 and Annex A, not from the Annex B field lists.** Server messages and Error Messages use UTF-8 JSON with `application/JSON`; App CReq/CRes uses JWE/JWS object handling and `application/jose`; Browser challenge carriage uses Base64url inside form fields where specified. Base64url is encoding, not encryption. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 5.1.1-5.1.3, pp. 111-112, Reqs 184-193 and 313; sections A.5.3-A.5.4, pp. 224-226, Tables A.2-A.3; sections 6.1.4 and 6.2.4, pp. 136-144]
5. **Annex C supplies a generic ECC key-pair generation procedure, not a new message channel or a complete ECDH protocol.** Chapter 6 explicitly invokes it for the SDK's Function I EC device-data key pair and for the SDK and ACS ephemeral pairs in Function J. Function K then uses the keys derived by Function J to protect App CReq/CRes. Annex C is not stated to govern TLS handshake keys, server-to-server messages, Browser messages, PReq/PRes, or RReq/RRes. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 6.2.2.1 and 6.2.3.1-6.2.3.2, pp. 139 and 141; Annex C, pp. 271-272]
6. **Annex D fills Chapter 6's deferred TLS profile.** It requires TLS 1.2 or higher, minimum RSA/ECC key sizes, named TLS 1.2 cipher-suite capabilities, P-256, DS-CA certificate support, and prohibited cipher families. It does not turn TLS transport into whole-message encryption and does not extend App JWE to server-to-server or Browser messages. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 6.1.2-6.1.4, pp. 135-137; Annex D, p. 273]

## 3. Annex C - ECC key-pair generation

### 3.1 Status of the procedure

Annex C observes that cryptographic libraries commonly provide EC key-pair generation. If such a function is unavailable, following ISO/IEC 15946-1 is recommended. It says the printed process **or its equivalent may be used**. Accordingly, Annex C does not require one API, random-number generator interface, integer representation, or exact code path. Chapter 6 still requires fresh key pairs at the functions that explicitly refer to Annex C. [Normative Recommendation / May plus Interpretation] [EMV 3DS v2.2.0, sections 6.2.2.1 and 6.2.3.1-6.2.3.2, pp. 139 and 141; Annex C, p. 271]

The Annex C input is curve parameters `(p, a, b, G, n, h)`. Output is a status and, on success, private key `d` plus public point `Q`; if generation errors, no `d` or `Q` should be returned. The note says the large 32- or 66-byte integers may be represented as byte strings rather than built-in integers. [Normative source description / Should / Note] [EMV 3DS v2.2.0, sections C.1-C.2, p. 271]

The printed process is: compute `N := len(n)` as the bit length of `n`; set `d := StringToInteger(Random(N))`; reject and repeat when `d > n - 2`; increment `d`; calculate `Q := PointMultiply(d, G, CurveID)`; return success with `d` and `Q`, otherwise return error. `StringToInteger`, `Random`, and `PointMultiply` are defined only at this abstract level. [Reference procedure / May] [EMV 3DS v2.2.0, section C.2.1, pp. 271-272]

### 3.3 Annex C discrepancy

The opening prose describes the desired private-key range as `1 < d < n`, which excludes `d = 1`. Section C.2 instead defines `d` in `[1, n - 1]`, and the printed process accepts a random integer from `0` through `n - 2` and then adds one, also producing `[1, n - 1]`. The output/process agree with each other but not with the strict lower bound in the introductory prose. Preserve the printed conflict and obtain authoritative clarification rather than silently changing the range. [Unresolved source inconsistency] [EMV 3DS v2.2.0, Annex C, p. 271]

## 4. Annex D - approved TLS versions and ciphers

### 4.1 Normative TLS profile

For links secured by TLS between the DS, 3DS Server, ACS, and SDK, the TLS version shall be 1.2 or higher. RSA keys shall be at least 2048 bits and ECC keys at least 256 bits. [Normative Requirement; Shall] [EMV 3DS v2.2.0, Annex D, p. 273]

For TLS 1.2, Annex D.1.1 names `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` and `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`. Curve P-256 shall be used and indicated in the “cipher suite extension.” The 3DS Server, ACS, and SDK shall support both suites; the DS shall support at least one. The DS CA shall provide client and server certificates for the suite or suites supported by the DS. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section D.1.1, p. 273]

Additional cipher suites may be supported for other reasons or legacy purposes, with interoperability testing at the implementer's discretion. This permission is constrained by D.2's absolute prohibition list; it is not permission to present or accept a prohibited suite. [Normative Permission plus Interpretation] [EMV 3DS v2.2.0, sections D.1.2-D.2, p. 273]

No offered or accepted suite may be Null, Anonymous/Anon, contain RC2, RC4, DES, IDEA, KRB5, ARIA, or MD5, or contain export-grade `EXPORT`. The note says 3DES and SHA-1 are being phased out and may become unsupported in a future version; it does not place them in this version's `shall not` list. [Normative Requirement plus Note] [EMV 3DS v2.2.0, section D.2, p. 273]
