# Security and Cryptography

## Scope and evidence method

This analysis covers Chapter 6 on physical PDF pages 133-144. The preserved PDF is the normative source. Only the corresponding extracted text was used for navigation, and every scoped physical page was inspected directly. Figure 6.1 (App-based security flow) on page 133, Figure 6.2 (Browser-based security flow) on page 134, and the supplemental Figure 6.3 (App security functions) on page 138 were visually verified. Chapter 6 contains no numbered requirement identifiers, so its citations use section and physical page without a requirement number. [Interpretation; evidence method] [EMV 3DS v2.2.0, chapter 6, pp. 133-144, Figures 6.1-6.3]

The evidence categories used below are **Normative Requirement**, **Interpretation**, **Issuer ACS Implementation Consideration**, **Scheme or Vendor Gap**, and **Unresolved**. Declarative security requirements are reported as written; implementation consequences and ordinary TLS mechanics are labelled as interpretations rather than attributed to EMVCo as additional requirements.

## 1. Verified security boundary

1. **TLS protects links, not the complete multi-hop route.** Links b and c are separate mutually authenticated TLS links. The DS terminates one link, processes the application message, and originates the next link; it is therefore an application intermediary that can see the AReq/ARes and RReq/RRes payloads it handles. A network intermediary that does not terminate TLS sees ciphertext, but a deployed TLS-terminating proxy can see plaintext at that termination point. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 6.1.2-6.1.3, pp. 135-136]
2. **Ordinary Browser and SDK Internet TLS authenticates the ACS server, not the client by certificate.** Links d and h require ACS server authentication using an ACS certificate signed by a commercial CA. Chapter 6 does not require a Browser or SDK client certificate on either link and does not require mutual TLS. [Normative Requirement plus Interpretation of the stated TLS roles] [EMV 3DS v2.2.0, sections 6.1.4 and 6.1.8, pp. 136-137]
3. **App CReq/CRes has two protection layers.** The direct SDK-ACS link uses server-authenticated Internet TLS, while the CReq/CRes JSON is additionally encrypted and integrity-protected as JWE with session keys established by the SDK-ACS secure-channel setup. This message-level layer is App-specific; Chapter 6 does not apply it to Browser CReq/CRes or the 3DS Method. [Normative Requirement plus Interpretation / evidence boundary] [EMV 3DS v2.2.0, sections 6.1.4.1 and 6.2.3-6.2.4, pp. 136 and 141-144]
4. **Device Information is not encrypted end-to-end to the ACS.** The SDK encrypts it for the DS and passes the JWE through the 3DS Server in `SDK Encrypted Data`. The DS decrypts it and inserts the plaintext Device Information into the AReq sent to the ACS over the separate DS-ACS mTLS link. The 3DS Server cannot read that JWE plaintext, but the DS and ACS can. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 6.2.2-6.2.2.2, pp. 138-140]
5. **Base64url is encoding, not encryption.** The verified Browser and 3DS Method handling rules use Base64url for browser-carried JSON/form values. Chapter 6 adds TLS to those links but specifies no Browser JWE/JWS layer. Anyone with application-layer access to the form or decoded value can recover the JSON; Base64url supplies neither confidentiality nor cryptographic integrity. [Interpretation; cross-reference] [EMV 3DS v2.2.0, sections 5.8.1-5.8.2, pp. 122-123; section 6.1.4.2 and 6.1.8, p. 137; sections A.5.3-A.5.4, pp. 224-226]
6. **A CA is a trust anchor, not a payload relay.** The DS CA signs the X.509 certificates used on links b and c and the ACS certificate used to sign App secure-channel setup content. A commercial CA signs the ACS certificate used for direct Internet TLS on links d and h. Merely issuing or signing these certificates does not put either CA on the application-data path. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 6.1.2-6.1.4 and 6.1.8, pp. 135-137; section 6.2.3.2, pp. 141-142]
7. **The security-flow figures are topology maps, not new message definitions.** Figures 6.1 and 6.2 label links a-h and state that dashed arrows and the 3DS Requestor are outside the 3DS specification and shown for clarity. The requirements come from the Section 6.1 link text; the figures must not be used to invent an API, payment-network control, or direct ACS-3DS Server result link. [Interpretation of figure note and link text] [EMV 3DS v2.2.0, chapter 6, pp. 133-137, Figures 6.1-6.2]

## 2. Why ordinary Browser TLS does not require a Browser certificate

In the Browser challenge and 3DS Method links, the Browser is the TLS client and the ACS is the TLS server. Server-authenticated TLS has the ACS present its server certificate and prove control of the corresponding private key; the Browser validates the ACS under its commercial-CA trust model. That authenticates the ACS endpoint to the Browser and establishes confidential, integrity-protected transport. It does **not** certificate-authenticate the Browser, the Cardholder, or an individual HTTP request to the ACS. Chapter 6 deliberately states only “ACS (server) authentication by the Browser” for these links. [Normative Requirement plus Interpretation of TLS roles] [EMV 3DS v2.2.0, sections 6.1.4.2 and 6.1.8, p. 137]

A Browser-held client certificate is needed only when the server requests certificate-based client authentication, as in mutual TLS. If an ACS, reverse proxy, enterprise policy, or other TLS endpoint is configured to request a client certificate, the Browser may display a certificate-selection prompt so the user can choose a suitable certificate/private-key identity. That prompt is evidence of a client-certificate request or local certificate policy; it is not part of the Chapter 6 Browser challenge or 3DS Method requirements. The Chapter 6 baseline for these links is server-authenticated TLS without a required Browser client certificate. [Interpretation; not an additional EMV 3DS requirement] [EMV 3DS v2.2.0, sections 6.1.4.2 and 6.1.8, p. 137]

Cardholder authentication inside the ACS challenge, and any Requestor login or session, are application-level functions. They must not be described as TLS client-certificate authentication unless an independently applicable design actually deploys mTLS. Likewise, Function H authenticates the Requestor App to the 3DS Requestor and checks the embedded SDK has not changed; it is not a requirement for an SDK client certificate on the SDK-ACS TLS link. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, section 6.1.1, pp. 134-135; section 6.2.1, p. 138]

### 3.1 3RI qualification

The note on page 137 says that for 3RI only the 3DS Server, DS, and ACS with links b and c “for AReq/ARes” apply. Section 3.4 nevertheless requires RReq/RRes for Decoupled 3RI. The general link-b/link-c RReq/RRes security definitions are not device-channel limited, yet the page-137 note omits their 3RI application. The matrix therefore reports the result-link controls as direct Chapter 6 requirements but assigns only Medium confidence to their explicit 3RI applicability pending source clarification. [Unresolved source scope] [EMV 3DS v2.2.0, section 3.4, pp. 76-77, Reqs 332-341 and 349-354; section 6.1.8, p. 137]

## 4. App-specific cryptographic functions

### 4.1 Function H - authenticity of the App and SDK

The 3DS Requestor must deploy an EMVCo-approved SDK embedded in its App and have a mechanism to authenticate the App to the Requestor, including confirmation that the embedded SDK has not changed. Chapter 6 does not prescribe the attestation, signature, API, device binding, certificate, or failure mechanism. This is an application/Requestor control and must not be converted into an asserted SDK-to-ACS mTLS requirement. [Normative Requirement plus Issuer/Requestor Implementation Consideration] [EMV 3DS v2.2.0, section 6.2.1, p. 138]

### 4.2 Function I - SDK encryption to the DS

The SDK selects the DS public key and encryption function from information supplied by the Requestor Environment, stops if the key cannot be identified, constructs the Device Information JSON, and encrypts it with JWE Compact Serialization. For an RSA DS key the supported parameters are `alg=RSA-OAEP-256`, `enc=A128CBC-HS256` or `A128GCM`, and no other parameters. For an EC DS key the SDK creates a fresh P-256 ephemeral pair and derives a 256-bit CEK using ECDH-ES with `apv=DirectoryServerID`. It then creates the JWE with `alg=dir`, `epk=QSDK`, either supported `enc`, and no other parameters. It uses a fresh 128-bit IV, uses the full CEK for CBC-HS256 or the leftmost 128 bits for GCM, and deletes the ephemeral pair. The separate printed `epk=PDS` line in the derivation block is treated as unresolved below. [Normative Requirement plus explicit source ambiguity] [EMV 3DS v2.2.0, section 6.2.2.1, pp. 139-140]

The DS decrypts `SDK Encrypted Data`; for the EC route it derives the CEK using its private key and the SDK ephemeral public key, and an EC-route decryption failure stops processing and is reported as an error. The DS then inserts the result as Device Information in the AReq sent to the ACS. JWE therefore provides confidentiality and integrity from SDK to DS across the Requestor/3DS Server intermediary, but it does not conceal Device Information from the DS and does not remain encrypted in the DS-ACS AReq. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, section 6.2.2.2, p. 140]

### 4.3 Function J - SDK-ACS key agreement and ACS authentication

The SDK generates fresh P-256 ephemeral key pair `(QC, dC)` and sends `QC` as `sdkEphemPubKey` in AReq. If a challenge is required, the ACS checks `QC`, generates fresh `(QT, dT)`, and derives 256 bits of keying material through ECDH-ES with `apv=SDK Reference Number`, `epk=QC`, and no other listed parameters. The profile says to assume an `enc` parameter of `ECDH-ES+A256KW` and a null algorithm ID for this Concat KDF, and the footnotes say RFC 7518 is used only for key derivation. The keys are associated with the ACS Transaction ID. No session key is sent through the 3DS Server or DS. [Normative Requirement] [EMV 3DS v2.2.0, sections 6.2.3.1-6.2.3.2, p. 141, source footnote 8]

The ACS signs a JWS payload containing its ephemeral public key, the SDK ephemeral public key, and the ACS URL. Supported signing algorithms are PS256 and ES256; RS256 is not in the supported pair, and source footnote 9 says PS256 is specified in preference to RS256. The `x5c` parameter carries the ACS X.509 certificate and available chain, and all other JWS parameters are absent. The certificate is signed by a DS CA whose public key is known to the SDK. The SDK validates the JWS with that DS-CA trust and must support both PS256 and ES256; validation failure stops processing and is reported as an error. The SDK derives the matching keys using `apv=SDK Reference Number` and `epk=QT`, deletes its ephemeral pair, and zeros its counters. Successful validation confirms to the SDK the ACS authenticity, freshness of the session keys, and correctness of the ACS URL. JWS authenticates and protects the integrity of the setup content but does not encrypt it. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, sections 6.2.3.2-6.2.3.3, pp. 141-143, source footnotes 9-10]

Chapter 6 does not give the ACS a corresponding SDK signing certificate or SDK signature to validate. The ACS checks the SDK public point and obtains key possession through successful protected-message processing, while Function H assigns App/SDK authenticity to the Requestor boundary. These facts must not be restated as certificate authentication of the SDK by the ACS. [Interpretation; evidence boundary] [EMV 3DS v2.2.0, sections 6.2.1 and 6.2.3, pp. 138 and 141-143]

### 4.4 Function K - CReq/CRes confidentiality, integrity, and sequencing

For SDK-to-ACS CReq, the SDK creates the Table B.3 JSON and encrypts it with JWE Compact Serialization using `alg=dir`, `kid=ACS Transaction ID`, either `A128CBC-HS256` or `A128GCM`, and no other parameters. CBC-HS256 uses the full `CEKS-A` and a fresh 128-bit random IV. GCM uses the leftmost 128 bits of `CEKS-A` and `SDKCounterStoA`, left-padded with `00` bytes, as the IV. The ACS decrypts with the same key identifier, checks that the received SDK counter equals its local counter, increments it, and stops with an error on decryption failure, mismatch, or counter wrap to zero. [Normative Requirement] [EMV 3DS v2.2.0, sections 6.2.4.1 and 6.2.4.3, pp. 143-144]

For ACS-to-SDK CRes, the ACS uses the same `enc` selected by CReq, `alg=dir`, the ACS Transaction ID as `kid`, and no other parameters. CBC-HS256 uses the full `CEKA-S` and a fresh 128-bit random IV. GCM uses the rightmost 128 bits of `CEKA-S` and `ACSCounterAtoS`, left-padded with `FF` bytes, as the IV. The SDK decrypts, checks the ACS counter against its local value, increments it, and stops with an error on decryption failure, mismatch, or counter wrap to zero. [Normative Requirement] [EMV 3DS v2.2.0, sections 6.2.4.2 and 6.2.4.4, pp. 143-144]

The counters supply message-order/freshness checking for this App secure channel and cause duplicate or out-of-order protected messages to fail the equality check. They are not a general replay rule for AReq/ARes, RReq/RRes, Browser traffic, 3DS Method traffic, or payment-network links. JWE provides authenticated encryption under the selected `enc`; it should not be described as “encoding.” [Interpretation bounded by the specified checks] [EMV 3DS v2.2.0, sections 6.2.4.1-6.2.4.4, pp. 143-144]

The source notes that `CEKA-S` and `CEKS-A` are extracted with the same 256-bit value in this version. Consequently, CBC-HS256 uses the same full 256-bit key in both directions. For GCM, the specification divides that material into different leftmost/rightmost 128-bit components for the two directions. This exception is explicit and should not be silently replaced with a preferred independent-key design. [Normative source note] [EMV 3DS v2.2.0, section 6.2.3.2, p. 142; sections 6.2.4.1 and 6.2.4.4, pp. 143-144]

### 7.2 Scheme, vendor, issuer, and implementation gaps

- **Payment System security requirements remain external.** Link a and any separate Requestor-Server integration must meet Payment System requirements, while links e/f/g receive no additional EMV 3DS security requirements. The applicable scheme security, onboarding, network, and mutual-authentication profiles must be obtained separately. [Scheme or Vendor Gap] [EMV 3DS v2.2.0, sections 6.1.1 and 6.1.5-6.1.7, pp. 134-137]
- **Certificate operations are not defined.** Trust-anchor installation, hostname/identity rules, issuance, revocation, expiry, renewal, rotation, pinning, key custody, and compromise response are not specified in these pages. Define them under the applicable DS, Payment System, CA, SDK, issuer, and platform profiles without attributing them to Chapter 6. [Scheme or Vendor Gap / Implementation Decision] [EMV 3DS v2.2.0, sections 6.1.2-6.1.4, 6.1.8, and 6.2.3, pp. 135-143]
- **TLS termination architecture is not prescribed.** A proxy or gateway that terminates TLS can see application plaintext on TLS-only links. If used, its trust, certificate, key, logging, and onward-protection design is an implementation decision; Chapter 6 does not authorize treating a TLS-terminating intermediary as opaque. [Issuer ACS Implementation Consideration] [EMV 3DS v2.2.0, sections 6.1.1-6.1.4 and 6.1.8, pp. 134-137]
- **Replay controls are link-specific.** App CReq/CRes has explicit counters and IV rules. Chapter 6 does not define universal application-message replay, duplicate-cache, idempotency, or uncertain-delivery handling for server-side, Browser, Method, or payment links. [Implementation Decision] [EMV 3DS v2.2.0, sections 6.2.4.1-6.2.4.4, pp. 143-144]
- **App/SDK authenticity mechanism is open.** Function H requires the outcome but does not define attestation, code signing, runtime integrity, device binding, or failure reporting. These must be designed under the SDK, Requestor, platform, and scheme profiles. [Issuer/Requestor Implementation Consideration] [EMV 3DS v2.2.0, section 6.2.1, p. 138]
- **External compliance is not established by TLS.** PCI DSS scope/compliance, scheme certification, privacy/data-protection duties, issuer security policy, secure-development controls, logging/redaction, HSM use, vulnerability management, and regulatory authentication rules are outside pages 133-144. TLS or Chapter 6 conformance alone must not be represented as satisfying them. [Scheme or Vendor Gap / Issuer Policy Decision] [EMV 3DS v2.2.0, chapter 6, pp. 133-144]
