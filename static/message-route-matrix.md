# EMV 3DS v2.2.0 Message Route Matrix

## Scope, evidence boundary, and reading rules

This is an issuer-side ACS routing reference for AReq/ARes, App and Browser CReq/CRes, RReq/RRes, Error Message (`Erro`), the 3DS Method, App OOB, Decoupled Authentication, and 3RI. The source PDF is normative. The project batch analyses were used as verified navigation aids; Figures 3.1, 3.3, and 3.4, the Browser and 3DS Method handling pages, the direct-link security pages, the Section 5.9 error pages, and the relevant browser/message-format tables were checked against the physical PDF. [Interpretation; evidence method] [EMV 3DS v2.2.0, sections 3.1-3.4, pp. 43-77, Figures 3.1, 3.3, and 3.4; sections 5.8-5.9, pp. 122-132; sections 6.1.2-6.1.4 and 6.1.8, pp. 135-137; sections A.5.4 and B.3-B.10, pp. 226 and 264-270]

The matrices use these rules:

- **Normative route:** AReq/ARes and RReq/RRes traverse two separate server-to-server application hops through the DS. The DS terminates one hop, processes the message, and initiates the next; the ACS and 3DS Server are never direct protocol peers for those messages. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, section 3.1, pp. 46-56, Reqs 12-24 and 33-75; section 3.3, pp. 61-70, Reqs 87-114 and 124-137; section 3.4, pp. 72-77, Reqs 275-283, 285-297, and 332-341]
- **Direct receiver:** The endpoint that receives this network hop. A logical payload creator can differ from the direct sender when a Browser carries a form. [Interpretation] [EMV 3DS v2.2.0, section 3.3, pp. 66-70, Reqs 117-140; sections 5.8.1-5.8.2, pp. 122-123, Reqs 259-270]
- **Parties not on direct path:** Components that may retain or later consume transaction state but do not terminate this hop. This is a topology interpretation of the verified figures and link definitions, not a statement that those parties lack all transaction data. [Interpretation] [EMV 3DS v2.2.0, sections 3.1, 3.3, and 3.4, pp. 44, 59, and 71, Figures 3.1, 3.3, and 3.4; sections 6.1.2-6.1.4 and 6.1.8, pp. 135-137]
- **Transport:** All 3DS message requests use HTTP POST over the applicable Section 6.1 secured connection, using HTTP/1.1 or later. Req 189 generally puts the corresponding response in the HTTP reply, but the Browser flow separately directs the final CRes through the Browser in a new POST to the Notification URL; that source-level exception/tension is preserved below. Server messages and Error Messages use UTF-8 `application/JSON`; App CReq/CRes use UTF-8 `application/jose`; Browser CReq uses `application/x-www-form-urlencoded`; Req 191 labels Browser CRes `text/html`. [Normative Requirement plus Unresolved source interaction] [EMV 3DS v2.2.0, sections 5.1.1-5.1.2, pp. 111-112, Reqs 184-191; section 3.3, p. 70, Req 140; section 5.8.2, p. 123, Req 269 and following final-CRes paragraph; section A.5.4, p. 226, Table A.3]
- **Security shorthand:** `b-auth` is 3DS Server-initiated DS-CA mTLS for AReq/ARes; `c-auth` is DS-initiated DS-CA mTLS for AReq/ARes; `c-result` is ACS-initiated DS-CA mTLS for RReq/RRes; `b-result` is DS-initiated DS-CA mTLS for RReq/RRes; `d-app` is ACS-server-authenticated commercial-CA TLS plus SDK-ACS JWE; `d-browser` is ACS-server-authenticated commercial-CA TLS without a Browser client certificate or Browser message-level JWE/JWS; `h-method` uses the same printed ACS server-authentication profile, while the source leaves an ACS-designated Method entity's certificate/integration profile outside scope. [Normative Requirement plus Interpretation / External Dependency] [EMV 3DS v2.2.0, section 3.3, p. 60, Reqs 83-85; sections 6.1.2-6.1.4 and 6.1.8, pp. 135-137; sections 6.2.3-6.2.4, pp. 141-144]
- **Response correlation:** Response fields, including Transaction IDs and Reference Numbers, must match the corresponding request. Rows that say “matching response IDs” apply this general rule; they do not imply that the independently generated Server, DS, ACS, and SDK IDs are aliases. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, section 5.1.6, p. 114, Req 212; section A.4, pp. 157, 164, 198, and 214, Table A.1]

## 3. ARes routes and disposition variations

An ARes with a non-challenge, non-Decoupled status completes the AReq/ARes route. For App and Browser, however, the ACS disposition requirements permit informational status `I` while the later 3DS Server handling branches enumerate `Y/A`, `C`, `N/U/R`, and `D` but omit `I`; its post-receipt handling is therefore unresolved. Status `C` prepares a challenge but does not execute it: the ACS supplies/stores challenge state and the direct challenge begins only after the SDK or Browser reaches the ACS. Status `D` establishes pending Decoupled state; no CReq/CRes is used and the final result arrives later in RReq. ## 5. RReq/RRes result-notification routes

RReq carries the server-side challenge or Decoupled result; RRes acknowledges the RReq. The ACS sends exactly one RReq for every ARes with status `C` or `D`. App and Browser final CRes, where applicable, is a separate client-side completion artifact and does not acknowledge RReq. [Normative Requirement plus Interpretation] [EMV 3DS v2.2.0, section 3.1, pp. 54-56, Reqs 62-79, especially Req 66; section 3.3, pp. 68-70, Reqs 124-140, especially Req 128; section 3.4, pp. 76-77, Reqs 332-341 and 349-354, especially Req 352]

The RReq/RRes field-set tables include `threeDSServerTransID`, `acsTransID`, and `dsTransID`; App rows can also carry `sdkTransID`. RReq additionally carries result/status, method/type, interaction, and cancellation fields under their message conditions; RRes carries `resultsStatus`. ## 6. Error Message (`Erro`) routes

`Erro` is the Message Type token for the Error Message. Its field set contains the available 3DS Server, ACS, DS, and SDK Transaction IDs plus Error Code, Error Component, Error Description, Error Detail, conditional Error Message Type, Message Type, and Message Version.
