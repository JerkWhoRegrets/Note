# App-based Challenge User Interface

## Scope and evidence method

This analysis covers Sections 4.1 and 4.2 on physical PDF pages 79-101. The PDF is the normative source. Extracted text was used for navigation and requirement discovery; every physical page in the range and every UI figure (Figures 4.1-4.18) was inspected directly. The supplemental data-element matrices on physical pages 165, 257-258, and 264-266 were also visually verified because Sections 4.1-4.2 refer to ACS UI Type, Table A.18, CReq, and CRes without restating every field name. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, sections 4.1-4.2, pp. 79-101, Figures 4.1-4.18; section A.4, p. 165; section A.8, pp. 257-258, Table A.18; sections B.3-B.4, pp. 264-266, Tables B.3-B.4]

The ordered protocol behavior for challenge-method selection, verification, repeat attempts, cancellation, result notification, and final CRes was already verified in Sections 3.1-3.2. Those requirements are cross-referenced here only where necessary to explain the UI state. [Interpretation; Cross-reference] [EMV 3DS v2.2.0, sections 3.1-3.2, pp. 50-58, Reqs 32 and 45-79]

The evidence categories used below are **Normative Requirement**, **Interpretation**, **Issuer ACS Implementation Consideration**, **Scheme or Vendor Gap**, and **Unresolved**. Requirement levels are stated as **Shall**, **Should**, **May**, **Note**, or **Descriptive (no modal)**. Sample content in a figure is not converted into a normative requirement.

## 1. Executive conclusions

1. **The standardized App challenge UI types are Text, Single Select, Multi Select, OOB, and HTML.** `acsUiType` values `01`-`05` identify those types. “OTP/Text” is the label used by the sample Text templates; OTP is not a sixth ACS UI Type. HTML Other is an experience within the HTML UI Type, not a new protocol value, and remains subject to HTML template guidance and specific DS rules. [Normative data-element definition plus Interpretation; Table / Descriptive] [EMV 3DS v2.2.0, section A.4, p. 165; sections 4.2.3 and 4.2.6.1, pp. 87-100, Figures 4.8-4.18]
2. **CRes carries ACS-selected presentation and challenge content; CReq carries the Cardholder/SDK response.** Native content is carried through the applicable CRes UI fields, while HTML is carried in `acsHTML`. Native text/single-select/multi-select input is represented by `challengeDataEntry`; HTML form input is represented by `challengeHTMLDataEntry`; resend, OOB continuation, cancellation, no-entry, and whitelisting have dedicated CReq elements. [Normative Requirement plus table mapping; Shall / Table] [EMV 3DS v2.2.0, sections 4.2.2-4.2.7, pp. 86-101, Reqs 158, 164-170, 362-378, and 387; sections A.8 and B.3-B.4, pp. 257-258 and 264-266, Tables A.18, B.3, and B.4]
3. **The SDK owns App presentation and interaction mediation; the ACS owns challenge content and completion state.** Native UI may be tuned by the SDK for the device, but HTML is displayed as supplied and is isolated in an SDK-owned web view. The ACS selects supported UI content, continues the challenge cycle, and signals completion in CRes through `challengeCompletionInd`. [Normative Requirement plus Descriptive; Shall / Descriptive] [EMV 3DS v2.2.0, sections 4.2.2, 4.2.4, 4.2.5, and 4.2.7, pp. 86-101, Reqs 153-170 and 362-378]
4. **“Get verification methods,” “send passcode,” and “verify passcode” are not standardized EMV 3DS messages.** The standardized App challenge messages are CReq and CRes; the named operations do not appear as protocol messages or CReq/CRes data elements. They may be useful issuer/ACS internal service boundaries, but their APIs, payloads, delivery channels, authentication, and error models are not specified here. [Issuer ACS Implementation Consideration; Interpretation / not standardized] [EMV 3DS v2.2.0, sections 2.4.3-2.4.4, pp. 34-35; section 3.1, pp. 50 and 53-54, Reqs 32 and 50-61; sections B.3-B.4, pp. 264-266, Tables B.3-B.4]
5. **Pages 79-101 do not state general accessibility, localization, or sensitive-input masking requirements.** Responsive HTML, device-aware Native tuning, structured zones, and expandable labels may assist implementations, and the figures show masked phone/email destinations, but these are not substitutes for normative accessibility, locale negotiation, content-language, or masking rules. [Interpretation; evidence boundary] [EMV 3DS v2.2.0, sections 4.1-4.2, pp. 79-101, Figures 4.1-4.18, Reqs 160-169 and 358-378]

## 2. General UI principles and responsibilities

### 2.1 Template zones and consistency

The UI is divided into four zones: the 3DS Requestor-managed Header zone at the top; the Branding zone for logos; the Challenge/Processing zone for challenge and progress content; and the Information zone for additional Cardholder information. The SDK must support all Device Rendering Options and, for Native UI, place ACS UI data in the applicable Table A.18 zones. The ACS must support at least one Native Device Rendering Option and HTML, and must create App HTML form elements in the applicable zones. [Normative Requirement plus Descriptive; Shall] [EMV 3DS v2.2.0, section 4.1, pp. 79-81, Figure 4.1, Reqs 314, 342, 358, and 359]

The App implementation may support Native, HTML, or both, based on Consumer Device capability. The source says the format **should** remain consistent throughout a CReq/CRes exchange; for example, a challenge that starts Native should remain Native. Supported image types are PNG, JPEG, TIFF, and BMP; other ACS image types may not be supported by the SDK. [Normative guidance plus Descriptive; Should / Descriptive] [EMV 3DS v2.2.0, section 4.2, pp. 81-82, Figures 4.2-4.3]

ADS is not a supported 3DS UI template. The ACS-provided Decoupled Authentication UI is outside EMV 3DS protocol scope. Cardholder Terms and Conditions are not supported in the templates unless regulatory requirements mandate their inclusion during payment authentication. [Normative notes / scope boundary] [EMV 3DS v2.2.0, section 4.1, p. 80]

## 3. Processing, presentation, and completion rules

### 3.1 Processing screens

For AReq/ARes, the SDK must create a processing screen, exclude other design elements, centre the processing graphic and optional DS logo, and store that logo. The Requestor App must display that SDK screen for the entire message cycle, for at least two seconds, with Cancel in the Header zone. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 4.2.1.1, pp. 83-84, Figure 4.4, Reqs 141-146 and 360]

For CReq/CRes, the SDK must use only the Consumer Device OS default processing graphic, without the DS logo or other design elements. The second and later cycles have a one-second minimum display; after submitting a Native CReq, the processing screen remains until CRes arrives or the timeout is exceeded. The same receive-or-timeout behavior applies to HTML. Cancel remains in the Header zone. [Normative Requirement; Shall] [EMV 3DS v2.2.0, sections 4.2.1.1, 4.2.4.1, and 4.2.7.1, pp. 84, 95, and 101, Figures 4.5-4.6, Reqs 147-148, 151, 153, 159, and 361]

The source notes that the spinning wheel remains through timeout/retry processing; the SDK may dim the challenge window or make the wheel translucent. If authentication succeeds the Cardholder returns to the merchant; otherwise the UI is updated to reinforce the expected action. These are notes, not numbered “shall” requirements. [Normative notes / guidance] [EMV 3DS v2.2.0, section 4.2.1.1, p. 86]

### 3.2 Native UI behavior

Native UI inherits the Requestor App look and feel while displaying Issuer-provided content and allowing Issuer/Payment System branding. The SDK may optimize formatting for screen and font size, so the line layout sent in CRes may not exactly match the display. It must nevertheless place supported fields in Table A.18 order/zones, interpret ACS-supplied carriage returns, and show no extra content in zones 2-4. Unsupported fields for the selected UI Type are omitted without sending an error; the challenge continues. [Normative Requirement plus Descriptive; Shall] [EMV 3DS v2.2.0, section 4.2.2, pp. 86-87, Reqs 362-364 and 387]

Expandable and Why labels are SDK-rendered controls; their associated text appears only after the user selects the corresponding label. If the ACS uses carriage returns in Challenge Information Text, Expandable Information Text, or Why Information Text, it must use the Table A.1 representation. Cancel is displayed at the top corner of the Header zone. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 4.2.2.1, pp. 86-87, Reqs 365-370]

### 3.3 HTML UI behavior

HTML gives the Issuer consistent branding, colours, and fonts across capable devices. The SDK displays the ACS HTML as supplied in an SDK-owned web view; unlike Native, it does not tune the ACS document. The ACS must create HTML form elements in the template zones and, when it uses the optional Expandable/Why fields, provide their labels and text for conditional display in the Information zone. [Normative Requirement plus Descriptive; Shall] [EMV 3DS v2.2.0, sections 4.2.5-4.2.6, pp. 95-97, Reqs 371-378]

The ACS HTML must be fully formed and responsive, with CSS, logos, images, and every other resource embedded. It must contain no external references, navigation attempts, or external resource requests. Submit must trigger a location change to `HTTPS://EMV3DS/challenge`; the ACS may thereby communicate through the SDK-mediated CReq/CRes channel but must not bypass the SDK or connect directly to itself. The SDK extracts `acsHTML`, builds the Requestor header above it, displays it in a web view, blocks external fetches, and processes Cardholder actions. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 4.2.7, p. 101, Reqs 160-170]

## 7. OTP and other verification-method lifecycle

1. **Method selection.** The ACS chooses the challenge method during challenge preparation, based on supported capabilities and its decisioning. `acsUiType` selects how the SDK renders the challenge, not necessarily the issuer authentication mechanism. A Text UI can carry an OTP experience, and HTML Other can carry a non-standard visual experience. [Normative Requirement plus Interpretation; Shall] [EMV 3DS v2.2.0, section 3.1, p. 50, Req 32; sections 4.2.3 and 4.2.6.1, pp. 87-100, Figures 4.8-4.18; section A.4, p. 165]
2. **Choice of delivery destination or method.** Figure 4.10 shows a Single Select example asking whether an OTP should go to a masked mobile number or email address. This is permitted UI content, not a required preliminary “get verification methods” call. The selection returns through CReq `challengeDataEntry`; the ACS can then prepare the next CRes. [Interpretation; sample figure / protocol mapping] [EMV 3DS v2.2.0, section 4.2.3, p. 90, Figure 4.10; sections B.3-B.4, pp. 264-266]
3. **Issuance and delivery.** The Text examples say that an OTP has been sent by text message, and resend produces a dedicated CReq request. The specification does not define how an OTP is generated, stored, delivered, rate-limited, or correlated inside the Issuer/ACS. Those actions occur before the ACS supplies the corresponding CRes content and may be implemented behind an internal “send passcode” boundary. [Issuer ACS Implementation Consideration; sample / not specified] [EMV 3DS v2.2.0, section 4.2.3, pp. 88-90, Figures 4.8-4.10; section B.3, p. 264]
4. **Entry.** The Cardholder enters the code in the SDK-rendered Native field or ACS HTML form. Native input goes in `challengeDataEntry`; HTML input goes in `challengeHTMLDataEntry`. [Normative protocol mapping; Table / figures] [EMV 3DS v2.2.0, sections 4.2.3 and 4.2.6-4.2.7, pp. 88-101, Figures 4.8-4.9 and 4.15-4.16; section B.3, p. 264]
5. **Verification.** After receiving CReq, the ACS checks the Cardholder-entered authentication data. On success it completes with `Y`; on incorrect input below its maximum it returns repeat CRes; at the maximum it completes with `N` and reason `19`. How the ACS calls an issuer credential/passcode engine is not specified and may be represented internally as “verify passcode,” but that is not an EMV 3DS message. [Normative Requirement plus Issuer ACS Implementation Consideration; Shall / not standardized] [EMV 3DS v2.2.0, section 3.1, pp. 53-54, Reqs 60-61; sections 4.2.1 and 4.2.3, pp. 84-86 and 93, Figures 4.5 and 4.13]
