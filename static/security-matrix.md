# Issuer ACS Security Matrix

## Scope, evidence, and classification

This is an issuer-side ACS security reference for the direct and cryptographically significant routes defined by EMV 3DS v2.2.0. The preserved PDF is the normative source. The security pass directly inspected physical PDF pages 34, 36, 48-50, 53-54, 57-58, 60, 64, 66, 70-71, 74-77, 112, 119-144, every page 148-222, 224-226, 265-266, 270, and 273. Chapter 6 and Annexes C-D contain no local numbered requirement identifiers, so those citations use section and physical page only. [Interpretation; evidence method] [EMV 3DS v2.2.0, sections 2.4-6.2, pp. 34-144; section A.4, pp. 148-222; sections A.5.3-A.5.4, pp. 224-226; sections B.4-B.5 and B.10, pp. 265-266 and 270; Annex D, p. 273]

Classification used below:

- **N - Normative:** a requirement or permission stated by the source.
- **I - Interpretation:** a bounded consequence of the cited topology or cryptographic mechanism, not an additional EMV 3DS requirement.
- **IC - Issuer ACS implementation consideration:** a recommended design choice; it is not made normative by this guide.
- **U - Unresolved or external dependency:** the Core specification is ambiguous, silent, or expressly defers the control.

`Not specified` never means prohibited, optional, or satisfied. It means the cited Core specification does not establish the control.

## 3. Flow qualification

- **App and App OOB.** Link d exists only if the transaction requires a challenge. App OOB continuation still uses the protected SDK-ACS CReq/CRes channel; the OOB communication method and the issuer/service-provider result integration are outside the EMV 3DS message set. [Normative Requirement plus boundary] [EMV 3DS v2.2.0, section 3.2, pp. 57-58; section 6.1.4.1, p. 136]
- **Browser.** Link d exists only for a challenge. The initial Browser CReq is one protocol message, while the ACS may require several HTML/form interactions before it sends RReq and, on normal completion after a valid RRes, produces the final CRes for the separate Notification URL return. Invalid RRes or inbound DS Erro instead uses Section 5.9.12's distinct non-Decoupled failure-CRes branch, whose content is not restated. [Normative Requirement plus Interpretation / Unresolved failure content] [EMV 3DS v2.2.0, section 5.8.2, p. 123, Reqs 267-270; section 5.9.12, pp. 131-132; section 6.1.4.2, p. 137]
- **3DS Method.** Method use is optional for the ACS and occurs before AReq. The Browser may connect to the ACS or an ACS-designated entity; how that entity gathers/returns values is outside scope. Its URL and TLS link are separate from the challenge URL/link, and the Browser-mediated completion callback is a second route to the Requestor Environment. [Normative Requirement / External Dependency] [EMV 3DS v2.2.0, section 3.3, p. 60, Reqs 83-85; section 5.8.1, pp. 122-123, Reqs 255-263 and 315; section 6.1.8, p. 137]
- **3RI.** The page-137 security note states generally that only the 3DS Server, DS, and ACS with link-b/link-c AReq/ARes apply to 3RI; there is no 3DS Client challenge or Method link. That AReq/ARes-only wording is a normative source statement, but limiting it to non-Decoupled 3RI would be an interpretation because Decoupled 3RI also requires result messages. [Normative source statement plus Unresolved scope] [EMV 3DS v2.2.0, section 3.4, pp. 76-77, Reqs 332-341 and 349-354; section 6.1.8, p. 137]
- **Decoupled 3RI.** Section 3.4 requires ACS->DS and DS->3DS Server RReq, followed by RRes on the same secure links, even though the page-137 summary says only AReq/ARes apply to 3RI. **Issuer ACS Implementation Consideration:** apply the general link-b/link-c result controls conservatively while obtaining authoritative clarification; do not present this treatment as a resolved Core requirement. [Unresolved source scope / Issuer ACS Implementation Consideration] [EMV 3DS v2.2.0, section 3.4, pp. 76-77, Reqs 330, 349-354 and 332-341; section 6.1.8, p. 137]
- **Decoupled issuer service.** How the Cardholder authentication decision is made is outside the Core specification. A direct ACS-to-issuer Authentication Service API shown with a dashed arrow must be treated as an internal/external issuer dependency, not as a new EMV 3DS protocol link. [Normative scope boundary plus Interpretation] [EMV 3DS v2.2.0, section 3.4, pp. 71 and 76, Figure 3.4, Req 330]

## 4. Cross-link cryptographic rules

### 4.1 Annex D baseline

For TLS links between the DS, 3DS Server, ACS, and SDK, TLS 1.2 or higher is required; RSA keys are at least 2048 bits and ECC keys at least 256 bits. For TLS 1.2, the 3DS Server, ACS, and SDK support both `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` and `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`; the DS supports at least one; P-256 shall be used and indicated in the printed “cipher suite extension”; and the DS CA provides client/server certificates for the suites the DS supports. Null/anonymous suites, export-grade suites, and suites containing RC2, RC4, DES, IDEA, KRB5, ARIA, or MD5 must not be presented or accepted. [Normative Requirement] [EMV 3DS v2.2.0, sections D.1.1-D.2, p. 273]

The source does not identify that printed “cipher suite extension” by TLS field or RFC; the obligation is preserved while the exact interoperability profile remains unresolved. [Unresolved] [EMV 3DS v2.2.0, section D.1.1, p. 273] [Related unresolved question](./unresolved-questions.md#source-ambiguity)

Annex D names DS, 3DS Server, ACS, and SDK, not Browser or 3DS Requestor. Its component capability rules must not be extended to Browser or link-a endpoints by inference; those use the Chapter 6 link-specific and applicable Payment System profiles. [Interpretation; applicability boundary] [EMV 3DS v2.2.0, section 6.1.1, pp. 134-135; sections 6.1.4.2 and 6.1.8, p. 137; Annex D, p. 273]

### 4.2 Base64url, JWS, JWE, and TLS visibility

- **N:** Browser CReq/CRes and the initial 3DS Method form value are Base64url encoded. **I/U:** Req 263 does not repeat the JSON/Base64url construction for the Method completion value; Annex A.5.3 Example 2 demonstrates it. **I:** Base64url is reversible formatting and supplies no confidentiality, integrity, authentication, or replay protection. [EMV 3DS v2.2.0, section 5.1.3, p. 112, Reqs 192-193; section 5.8.1, pp. 122-123, Reqs 260 and 263; sections A.5.3-A.5.4, pp. 224-226, Tables A.2-A.3]
- **N:** ACS Signed Content is a JWS that binds the ACS ephemeral public key, SDK ephemeral public key, and ACS URL. **I:** JWS protects authenticity/integrity but does not conceal its payload. [EMV 3DS v2.2.0, sections 6.2.3.2-6.2.3.3, pp. 141-143]
- **N:** App CReq/CRes and SDK Device Information use JWE under their respective profiles. **I:** this remains message-level protection even when an HTTP/TLS gateway terminates the outer TLS session. [EMV 3DS v2.2.0, sections 6.2.2-6.2.4.4, pp. 138-144]
- **I:** a CA signs/validates certificate trust; it is not a payload relay merely because it issued a certificate. DS and commercial CAs are not on application-data paths solely in their CA role. [EMV 3DS v2.2.0, sections 6.1.2-6.1.4 and 6.1.8, pp. 135-137]

## 5. Issuer ACS implementation considerations

The following controls are recommendations. They are not protocol requirements in the cited pages.

- **IC - TLS termination and segmentation:** Treat any reverse proxy, load balancer, API gateway, or service-mesh sidecar that terminates TLS as a plaintext trust boundary. Authenticate onward workloads, re-protect internal hops, and restrict which systems may terminate link-b/link-c mTLS or Internet TLS. Chapter 6 specifies endpoint link properties but not proxy or onward-encryption architecture. [EMV 3DS v2.2.0, sections 6.1.1-6.1.4 and 6.1.8, pp. 134-137]
- **IC - Logging and redaction:** Core requires transaction information to be logged as required by DS rules at identified App, Browser, and 3RI steps, but it does not supply a self-contained logging or redaction standard. Use an allowlist for production logs. Prefer transaction identifiers, message type/version, status, error code, route, latency, certificate fingerprint/serial, and cryptographic-operation outcome. Redact or omit PAN/account data, Cardholder challenge entry, OTP/passcode values, Device Information, Authentication Value, decrypted JWE bodies, CEKs/session keys, private keys, and unbounded HTML/form content. Separate audit evidence from payload capture and apply access/retention controls. [Normative Requirement plus Issuer ACS Implementation Consideration] [EMV 3DS v2.2.0, section 3.1, pp. 51 and 56, Reqs 36 and 73; section 3.3, pp. 65 and 69, Reqs 113 and 135; section 3.4, pp. 75 and 77, Reqs 296, 339, and 341; sections 6.1-6.2, pp. 134-144; section A.4, pp. 148-222, Table A.1]
- **IC - Certificate lifecycle:** Maintain separate inventories and rotation plans for DS-CA link-b/link-c client/server credentials, the commercial-CA ACS Internet certificate, and the DS-CA-signed ACS JWS signing certificate. Define identity/SAN validation, trust-anchor distribution, issuance, revocation checking, overlap, expiry alarms, emergency rollover, private-key custody, and compromise response with the applicable DS, scheme, CA, SDK, and issuer policies. [EMV 3DS v2.2.0, sections 6.1.2-6.1.4, 6.1.8, and 6.2.3, pp. 135-143; Annex D, p. 273]
- **IC - Private/session key custody:** Keep long-term TLS and JWS signing keys in an issuer-approved protected key service or equivalent controlled boundary. Associate SDK-ACS channel state and counters with the ACS Transaction ID, synchronize them across the ACS cluster, fail closed on lost/corrupt state, and delete ephemeral/session material after the defined terminal state. The source requires fresh/deleted ephemeral keys and counter processing but does not prescribe HSM use, cluster synchronization, restart recovery, or terminal-state retention. [EMV 3DS v2.2.0, sections 6.2.2.1-6.2.4.4, pp. 139-144]
- **IC - Browser data handling:** Do not place decoded CReq/CRes, Method data, challenge input, or session data in URLs, analytics, console logs, or referrer-bearing resources. Treat Base64url form values as plaintext at the Browser and web application layers, and constrain ACS HTML/resource origins under issuer web-security policy. [EMV 3DS v2.2.0, sections 5.8.1-5.8.2, pp. 122-123; sections A.5.3-A.5.4, pp. 224-226]
- **IC - Issuer service links:** Define authenticated, confidential, integrity-protected, replay-resistant, least-privilege interfaces for ACS connections to OTP delivery/verification, OOB, Decoupled Authentication Service, fraud/risk, customer profile, key-management, observability, and audit services. These are issuer/internal or vendor interfaces, not EMV 3DS protocol messages, and their exact security profile must come from issuer, scheme, vendor, PCI, and regulatory requirements. The Core specification expressly leaves the OOB/Decoupled decision mechanism outside scope. [EMV 3DS v2.2.0, section 3.2, pp. 57-58; section 3.4, pp. 71 and 76, Figure 3.4, Req 330]
- **IC - Privacy and audit separation:** Minimize plaintext exposure to components that require it, separate operational metrics from authentication evidence, and define access, retention, deletion, legal hold, and incident-response controls for Device Information, challenge data, and identifiers. Chapter 6 transport/cryptographic controls alone do not define or prove privacy, PCI, scheme, or regulatory compliance. [EMV 3DS v2.2.0, chapter 6, pp. 133-144]
