# Foundations and Overview

## Scope and evidence method

This analysis covers Chapters 1 and 2 on physical PDF pages 15-42. It treats the PDF as normative, uses the extracted text only for navigation, and verifies tables and figures against rendered physical pages.

Each conclusion below uses one of the required labels. "Normative Requirement" is reserved for an explicit mandatory or defined specification rule. "Interpretation" identifies a compact synthesis of descriptive text or figures. "Issuer ACS Implementation Consideration" identifies an implementation consequence for an issuer-controlled ACS. "Scheme or Vendor Gap" identifies a matter assigned to a Payment System, DS programme, 3DS Integrator, or other external implementation. "Unresolved" identifies an ambiguity or a point not established in these pages.

Requirement levels are recorded as **Shall**, **Should**, **May**, **Note**, **Definition**, or **Descriptive (no modal)**.

No numbered `Req` marker occurs in Chapters 1 or 2; all citations in this analysis therefore omit a requirement number.

## 6. EMV 3DS protocol messages versus HTTP/TLS transport

| Conclusion | Actor | Flow/channel | Message | Requirement level | Finding and evidence |
|---|---|---|---|---|---|
| Interpretation | All 3DS components | All | PReq/PRes, AReq/ARes, CReq/CRes, RReq/RRes, Error | Descriptive / referenced standards | EMV 3DS names the application-level message families and their senders, recipients, content purpose, and flow. HTTP and TLS are separately referenced standards: HTTP supplies web transfer semantics, and TLS supplies confidential transport. A protocol message is therefore not itself "HTTP" or "TLS"; it is carried over a transport/link that can use them. [EMV 3DS v2.2.0, sections 1.3 and 1.5, pp. 16 and 25; section 2.4, pp. 34-35] |
| Interpretation | Browser, 3DS Server, ACS | Browser-based | CReq/CRes and browser interactions | Definition / Descriptive (no modal) | The browser is a conduit for messages between the Server side and ACS. Browser-based Requestor/Server communication uses a TLS browser connection, and browser challenge posting is directed to the ACS URL from ARes. | Interpretation | 3DS Server, DS, ACS, DS CA | Server-to-server links | AReq/ARes, RReq/RRes, PReq/PRes as applicable | Descriptive (no modal) | TLS client/server certificates cover the 3DS Server-DS and DS-ACS communications; signing certificates cover ACS-to-SDK messages.
