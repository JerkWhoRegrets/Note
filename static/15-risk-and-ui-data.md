# EMV 3DS v2.2.0 Risk and UI Data

## 1. Scope and interpretation rules

This batch covers Annex A.7, **3DS Requestor Risk Information**, and Annex A.8, **UI Data Elements**, on physical PDF pages 237-258. Physical page 237 intentionally overlaps the prior batch: it finishes section A.6.3 and then starts A.7. Annex A.8 starts on physical page 257, and Table A.18 ends on physical page 258 immediately before Annex B. [EMV 3DS v2.2.0, sections A.6.3-A.8, pp. 237-258, Tables A.8-A.18; no local numbered Reqs]

Annex A.7 says the 3DS Requestor supplies four optional risk-information objects in AReq to support ACS risk assessment. Their presence can make risk-based authentication more precise and reduce unnecessary challenges. Those four protocol objects are Cardholder Account Information, Merchant Risk Indicator, 3DS Requestor Authentication Information, and 3DS Requestor Prior Transaction Authentication Information. Sections A.7.5-A.7.10 then detail separate rendering, challenge-input, status, and image structures; those are not children of the four Requestor risk objects. [EMV 3DS v2.2.0, section A.7, p. 237]

The Table A.1 `R`, `C`, and `O` rules remain controlling for each parent protocol field. The A.7 child tables do not contain an inclusion column. A.7.1 and A.7.2 expressly call their detailed child fields optional; A.7.3-A.7.6 and A.7.9-A.7.10 do not assign child-level `R`, `C`, or `O` codes. This analysis therefore preserves the parent-field rule and does not invent mandatory child fields. [EMV 3DS v2.2.0, Annex A and sections A.1-A.2, pp. 145-147; section A.7, pp. 237-256, Tables A.8-A.17]

Privacy/security and ACS implementation observations below are explicitly non-normative unless the text says that the source itself states the point. They identify likely handling sensitivity without adding validation, retention, cryptographic, or scheme requirements. No local numbered requirements occur in A.7-A.8; Requirement 314 is cited only where the source itself cross-links the SDK rendering capability. [EMV 3DS v2.2.0, section 4.1, p. 80, Req 314; sections A.7-A.8, pp. 237-258]

### 4.3 Challenge Data Entry - `challengeDataEntry`

`challengeDataEntry` is a top-level App CReq String, not a structured child object. Table A.1 makes it conditionally required when ACS UI Type is `01`, `02`, or `03`, challenge data was entered, and `challengeCancel` and `resendChallenge` are absent. It is sourced by the SDK and consumed by the ACS. As Cardholder-entered authentication data, it is highly sensitive and should be excluded from ordinary logs, analytics, traces, and support views as an issuer implementation control. [EMV 3DS v2.2.0, section A.4, p. 191, Table A.1]

Table A.14 applies only when `challengeDataEntry` is missing and assumes no other errors. Its columns refer to four separate top-level CReq fields: `challengeDataEntry`, `challengeCancel`, `resendChallenge`, and `challengeNoEntry`. The table is a message-handling matrix, not a JSON object. [EMV 3DS v2.2.0, section A.7.7, p. 252, Table A.14]

|---|---|---|---|---|---|---|
| Missing | `01`, `02`, or `03` | Missing | Missing | Present with `Y` | Assume no challenge data was entered; send CRes to the SDK, not an Error Message | [EMV 3DS v2.2.0, section A.7.7, p. 252, Table A.14] |
| Missing | `01`, `02`, or `03` | Present | Missing | Missing | Send CRes to the SDK | [EMV 3DS v2.2.0, section A.7.7, p. 252, Table A.14] |

### 4.4 Transaction Status Conditions - `transStatus`

`transStatus` is a top-level one-character String sourced by the ACS or DS. For PA, Table A.1 requires it in ARes, RReq, and final CRes; NPA presence is conditional under DS rules. Final CRes permits only `Y` or `N`, and `C` is invalid when Requestor Challenge Indicator is `06`. Table A.15 adds the exact message-validity conditions below. ## 6. ACS/risk-engine and UI implementation boundary

The normative data flow is: the Requestor supplies the four optional AReq risk objects; the ACS evaluates available values as risk-assessment inputs; the ACS may use better data to reduce unnecessary challenges; and, if a Native App challenge is selected, the rendering capability, template, CRes UI fields, SDK Cardholder input, and status rules govern the protocol/UI exchange. The specification does not prescribe a score, feature weighting, threshold, model, fallback, allow/deny rule, issuer database, or private risk-engine API. [EMV 3DS v2.2.0, section A.7, p. 237; sections A.7.1-A.7.8, pp. 238-254]

Issuer ACS implementation considerations, not Annex A requirements:

- Retain the exact parent object and field provenance. A missing optional value is not the same as zero, false, guest, no suspicious activity, or no prior authentication. [Protocol anchor: EMV 3DS v2.2.0, sections A.7.1-A.7.4, pp. 238-249, Tables A.8-A.11]
- Validate only printed types, lengths, formats, and values. Do not add numeric ranges to the count strings, child-required rules, array uniqueness, or date/indicator precedence without another authoritative profile. [Protocol anchor: EMV 3DS v2.2.0, section A.2, p. 147; sections A.7.1-A.7.6, pp. 238-251, Tables A.8-A.13]
- Minimize, restrict, and redact account history, delivery email, suspicious-activity, authentication evidence, and prior-transaction identifiers according to applicable privacy, issuer, scheme, and security obligations; A.7 itself does not supply retention or logging rules. [Protocol anchor: EMV 3DS v2.2.0, section A.7, pp. 237-249, Tables A.8-A.11]
- Treat `threeDSReqAuthData` and `threeDSReqPriorAuthData` as opaque until the applicable method/profile defines their content and verification. Do not mistake either for `sdkEphemPubKey`, an SDK private key, or ACS-native issuer evidence. [Protocol anchor: EMV 3DS v2.2.0, section A.4, p. 213, Table A.1; sections A.7.3-A.7.4, pp. 246-249, Tables A.10-A.11]
