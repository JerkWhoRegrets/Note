This analysis covers Section 3.3 on physical PDF pages 59-70. The PDF is the normative source. Extracted text was used only for navigation. Every physical page in the range, Figure 3.3, its loop and dashed-arrow legend, all source notes, and both footnotes were inspected directly. ## 1. Verified topology and orchestration boundary

1. **Figure 3.3 is a possible Requestor Environment arrangement, not a prescribed deployment.** The figure groups Browser and 3DS Requestor within the Requestor website and shows 3DS Server separately. Dashed arrows are not part of the EMV 3DS protocol. [Interpretation; Note / Descriptive (no modal)] [EMV 3DS v2.2.0, section 3.3, p. 59, Figure 3.3]
2. **Authentication orchestration remains server-side.** AReq travels 3DS Server -> DS -> ACS and ARes returns ACS -> DS -> 3DS Server. For a challenge, the ACS later sends RReq ACS -> DS -> 3DS Server and receives RRes back through the DS. The DS validates, routes, and logs these server-side messages; the 3DS Server assembles AReq, chooses the DS, validates ARes/RReq, and supplies the result to the Requestor Environment. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, pp. 61-66 and 68-70, Reqs 87-118 and 124-140]
3. **The browser links are deliberately narrower.** The Method link carries the hidden-iframe Method exchange. The separate challenge link carries the single browser CReq, ACS UI/HTML, and Cardholder submissions; final CRes is then carried through the browser to the Requestor Notification URL. None of these browser exchanges replaces DS routing of AReq/ARes or RReq/RRes. [Interpretation; Shall / Descriptive] [EMV 3DS v2.2.0, section 3.3, pp. 60 and 66-70, Reqs 84-85, 117, and 119-140; sections 6.1.4.2 and 6.1.8, p. 137]
4. **The DS is absent from the direct browser challenge transport, and the 3DS Server is not an on-path HTTP intermediary for the browser-to-ACS POST.** Req 117 assigns CReq construction to the 3DS Server, while Req 267 assigns it to the 3DS Requestor; the internal author is unresolved. The ACS retains challenge/result state, and the DS retains the 3DS Server URL with DS Transaction ID for RReq routing. [Interpretation plus Normative Requirement / Unresolved CReq author; Shall] [EMV 3DS v2.2.0, section 3.3, pp. 63-66 and 69, Reqs 99, 109, 117, and 129-133; section 5.8.2, p. 123, Req 267]

For the initial CReq, ACS UI, and Cardholder submissions, the immediate peers are Browser and ACS: DS, 3DS Server, and the 3DS Requestor endpoint are not on that direct network path. For final CRes, the Browser posts to the Notification URL supplied by the 3DS Server in the Requestor Environment. DS is not on that Browser hop, but the source conflicts on whether the terminating component is described as the 3DS Requestor or 3DS Server, so the 3DS Server must not be excluded. ACS retains challenge and RReq state, DS retains result-routing state, and the 3DS Server receives the final challenge status through RReq independently of the Browser return. [Interpretation plus Unresolved recipient wording] [EMV 3DS v2.2.0, section 3.3, pp. 63-70, Reqs 99, 109, and 117-140; sections 5.9.6 and 5.9.12, pp. 127 and 131-132, source footnote 7; section A.4, p. 206, Table A.1; section A.5.4, p. 226, Table A.3]

### Why the 3DS Server and DS still orchestrate the transaction

The browser-ACS challenge link is a presentation and Cardholder-interaction path, not the complete authentication control plane. The 3DS Server has already selected the DS and created the AReq, which carries the Notification URL used after the challenge. The DS routes and validates AReq/ARes and stores the server return URL. The ACS's `C` decision and ACS URL arrive in ARes through that server-side path. After the ACS decides the challenge outcome, RReq/RRes carries the result through the DS to the 3DS Server before the ACS posts final CRes to the browser-side Notification URL. This is why direct browser-ACS interaction coexists with 3DS Server and DS orchestration. [Interpretation; Shall / Descriptive] [EMV 3DS v2.2.0, section 3.3, pp. 62-70, Reqs 90-140]

## 2. 3DS Method invocation and correlation

### 2.1 Invocation sequence

1. The 3DS Requestor asks the 3DS Server for ACS/DS protocol-version ranges and, when present in cached PRes card-range data, the 3DS Method URL. The 3DS Server generates `threeDSServerTransID` and returns it with the version and Method URL data through the Requestor Environment. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, p. 60, Reqs 80-82]
2. When a Method URL exists for the transaction, the Method must execute on the Requestor website. The 3DS Server must ensure the `threeDSServerTransID` used for the Method is the same value later placed in AReq. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, p. 60, Reqs 83-84]
3. Req 261 assigns creation of the hidden HTML iframe and HTTP form to the 3DS Requestor, while Section 6.1.8 says the 3DS Server loads the iframe; that internal actor conflict is unresolved. The form field is named `threeDSMethodData`; its initial value is a Base64url-encoded JSON object containing `threeDSServerTransID` and `threeDSMethodNotificationURL`. The browser posts that form to the ACS 3DS Method URL over a server-authenticated TLS link. [Normative Requirement plus unresolved source inconsistency; Shall] [EMV 3DS v2.2.0, section 5.8.1, p. 122, Reqs 259-262; section A.5.3, pp. 224-225; section 6.1.8, p. 137]
4. The ACS, or an entity it designates, interacts with the hidden iframe to collect additional browser/device information. Which data is gathered and how it is retrieved or used are outside the specification. The ACS must store the applicable values with `threeDSServerTransID` so that it can match them when AReq later arrives with the same ID. [Normative Requirement plus Scheme or Vendor Gap; Shall / explicitly out of scope] [EMV 3DS v2.2.0, section 3.3, p. 60, Req 85; section 5.8.1, p. 122, Req 262]
5. On completion, the ACS recalls `threeDSServerTransID` and causes the iframe to HTTP POST another `threeDSMethodData` form to `threeDSMethodNotificationURL`. Req 263 requires the completion field to contain the recalled ID but does not restate JSON/Base64url construction; Annex A.5.3 Example 2 demonstrates a Base64url-encoded JSON object containing that ID. The notification URL itself was present only in the initial Method data. The 3DS Server sets the Method Completion Indicator to `Y` on notification, `N` if the Method does not complete within 10 seconds, or `U` when no Method URL exists. [Normative Requirement plus example-backed Interpretation / Unresolved completion encoding; Shall] [EMV 3DS v2.2.0, section 5.8.1, pp. 122-123, Reqs 258-263 and 315; section A.5.3, pp. 224-225, Table A.2 and Example 2]
6. The Method call must occur before AReq for the same transaction. Once completion notification is received, the 3DS Server can submit AReq. The common `threeDSServerTransID` is the protocol-defined correlation between pre-AReq browser data and the later AReq; a browser cookie is not specified for that purpose. [Normative Requirement plus Interpretation; Shall / Note] [EMV 3DS v2.2.0, section 3.3, p. 60, Req 83; section 5.8.1, pp. 122-123, Reqs 257, 262, and 315]

### 2.2 What `threeDSMethodData` is and is not

`threeDSMethodData` is the name of an HTTP form field. Req 260 explicitly defines its initial value as a Base64url-encoded JSON object containing `threeDSServerTransID` and `threeDSMethodNotificationURL`. Req 263 says the completion POST reuses the field name and returns the recalled `threeDSServerTransID`, but it does not repeat the JSON/Base64url construction; Annex A.5.3 Example 2 demonstrates that representation. It is not an AReq, CReq, or browser session cookie. [Normative Requirement plus Interpretation / Unresolved completion wording] [EMV 3DS v2.2.0, section 5.8.1, pp. 122-123, Reqs 259-263; section A.5.3, pp. 224-225, Table A.2]

## 3. Browser frictionless flow

1. The Requestor Environment gathers the data required for AReq and makes it available to the 3DS Server. Pages 60-61 list possible account, risk, prior-authentication, payment/non-payment, and Cardholder information, but do not assign each item to a specific internal component. Browser-to-Requestor communication must use server-authenticated TLS; a separate Requestor-to-3DS Server link must meet Payment System security requirements with mutual authentication when those are separate components. [Normative Requirement plus Interpretation; Shall / Descriptive] [EMV 3DS v2.2.0, section 3.3, pp. 60-61, Reqs 86 and 301]
2. The 3DS Server obtains its identifiers, checks AReq data availability, selects the DS, establishes the secure link, formats AReq, and sends it to the DS. The DS validates AReq, creates the DS Transaction ID, performs version/range/reference checks, stores the 3DS Server URL with DS Transaction ID, and forwards AReq to the ACS. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, pp. 61-63, Reqs 87-101]
3. The ACS validates AReq, checks device and account support, generates the ACS Transaction ID, and decides the disposition. In a frictionless transaction it must not initiate Cardholder interaction. For `Y` or `A`, payment authentication includes the DS-defined ECI and Authentication Value in ARes. [Normative Requirement; Shall / Should for named decision inputs] [EMV 3DS v2.2.0, section 3.3, pp. 63-64, Reqs 102-108 and 319]
4. ARes returns ACS -> DS -> 3DS Server. At the 3DS Server, an ARes with `Y` or `A` supplies the Transaction Status, ECI, and Authentication Value for authorisation and the necessary ARes information is passed to the Requestor Environment. Frictionless processing then moves to checkout at Step 22; no CReq/CRes or RReq/RRes occurs. [Normative Requirement; Shall / Note] [EMV 3DS v2.2.0, section 3.3, pp. 65-67, Reqs 110-116]

### 3.1 Browser Decoupled branch at the common ACS disposition

For a Browser Decoupled transaction with Transaction Status `D`, the ACS shall start a timer against 3DS Requestor Decoupled Max Time and authenticate the Cardholder asynchronously. The authentication decision method is outside scope, while the stated ACS objective is to finish before the Max Time expires. [Normative Requirement plus explicit scope boundary; Shall / objective] [EMV 3DS v2.2.0, section 3.3, p. 65, Req 326]

## 4. Browser challenge preparation and processing

### 4.1 Challenge preparation

1. If the ACS selects a browser challenge, it sets Transaction Status `C`, sets the ACS URL used for the browser-to-ACS link, and stores `threeDSServerTransID`, DS URL, and DS Transaction ID for later RReq processing. It then formats and returns ARes through the DS. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, pp. 64-65, Reqs 109-114]
2. The 3DS Server validates ARes and evaluates whether the Requestor will perform the requested challenge. If accepted, it passes the needed ARes data to the Requestor Environment, and the form is posted through the Browser to the ACS URL over server-authenticated TLS, optionally with `threeDSSessionData`. Req 117 assigns formatting, Base64url encoding, form construction, and POST initiation to the 3DS Server; Req 267 instead says the 3DS Requestor generates the CReq, iframe, and POST, so the internal author remains unresolved. [Normative Requirement plus unresolved source inconsistency; Shall] [EMV 3DS v2.2.0, section 3.3, pp. 66-67, Reqs 115-117; section 5.8.2, p. 123, Reqs 266-268; section A.5.4, p. 226, Table A.3]
3. If the Requestor declines the requested challenge, the browser challenge is not launched. The 3DS Server still receives and validates the later RReq, returns RRes, and any further processing is outside 3DS processing; it may continue to checkout. [Normative Requirement; Shall / May] [EMV 3DS v2.2.0, section 3.3, p. 66, Req 117]

### 4.2 Challenge processing

1. The ACS receives the single protocol CReq from the browser, validates it, prepares the ACS UI, and sets Interaction Counter to zero. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, p. 67, Reqs 119-121; section 2.4.3, p. 34]
2. The ACS sends UI HTML to the browser in response to the challenge POST. The browser displays it; the Cardholder enters authentication data; and the browser sends that entered data to the ACS. Redirects must remain within authentication purposes, and external resources must be limited to those needed for authentication experience and security. These HTML, JavaScript, resource, redirect, and form-submission exchanges are browser traffic, not additional CReq/CRes protocol messages. [Normative Requirement plus Interpretation; Shall / Descriptive] [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 122-123 and 307]
3. On incorrect input below the ACS maximum, the ACS prepares another ACS UI and returns to the HTML exchange. The source explicitly says HTML exchange repeats until the ACS determines an outcome. On success it sets `Y`, ECI, and Authentication Value; at the maximum it sets `N`, reason `19`, and the DS-defined ECI. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, p. 68, Req 123]
4. The ACS formats RReq, establishes the result link to the DS, and sends exactly one RReq for the ARes with `C`. The DS uses the AReq-derived 3DS Server URL to forward RReq to the 3DS Server. The server validates RReq and returns RRes through the DS to the ACS. [Normative Requirement; Shall] [EMV 3DS v2.2.0, section 3.3, pp. 68-70, Reqs 124-137]
5. Only after the RReq/RRes exchange does the ACS format and Base64url-encode final CRes and cause an HTTP POST through the browser to the Notification URL that was supplied in AReq. The Requestor Environment receives the `cres` form field, conveys the result to its components, and closes the challenge window. [Normative Requirement; Shall / Descriptive] [EMV 3DS v2.2.0, section 3.3, p. 70, Reqs 138-140; section 5.8.2, p. 123, Req 270; section A.5.4, p. 226, Table A.3]

## 7. Protocol messages, HTTP exchanges, and state

### 7.1 One browser CReq/CRes pair, multiple HTML interactions

For the browser channel, the specification says there is only one CReq and one CRes per challenge. Figure 3.3 shows one CReq at Step 11 and one completion CRes at Step 21. The loop in Steps 12-15 is explicitly an exchange of HTML/UI and Cardholder submissions until the ACS determines an outcome. Multiple HTTP requests/responses may therefore occur inside one browser challenge without creating additional protocol CReq/CRes pairs. [Normative Requirement plus Interpretation; Descriptive / Shall] [EMV 3DS v2.2.0, sections 2.4.3-2.4.4, pp. 34-35; section 3.3, pp. 59 and 67-70, Figure 3.3, Reqs 119-140; section 5.8.2, p. 123]

**Implementation Inference.** The phrases "channel established by the HTTP POST" and "using the secure link established in Step 10" describe the logical, TLS-protected browser challenge path. They do not require a single HTTP request, TCP connection, or TLS connection to remain open across UI rendering, user think time, repeat HTML interactions, RReq/RRes, and the final return POST. Connection reuse is an HTTP/browser/server implementation matter. The specification separately states that the Method URL and challenge URL establish separate TLS links. [Implementation Inference; not a protocol requirement] [EMV 3DS v2.2.0, section 3.3, pp. 67 and 70, Reqs 122 and 140; sections 6.1.4.2 and 6.1.8, p. 137]

### 7.2 Three distinct layers

| Layer | Example | What it means |
|---|---|---|
| EMV 3DS protocol message | AReq/ARes, the one browser CReq/CRes pair, RReq/RRes | A defined JSON protocol payload with EMV 3DS semantics and transaction identifiers. |
| HTTP request/response carrying or supporting the protocol | Form POST field `creq`, form POST field `cres`, Method form field `threeDSMethodData`, HTTP response carrying ACS UI | Web transport/envelope. A form field can contain a Base64url protocol JSON message, but the HTTP request is not itself the protocol message. |
| Other browser navigation/UI traffic | ACS HTML, JavaScript, authentication-data form submission, redirect, logo/resource fetch, parent-page refresh, iframe removal | Browser interaction required to present and complete the challenge. These calls are not additional CReq/CRes messages unless they actually carry the defined `creq` or `cres` payload. |

This separation is a synthesis of the defined message cardinality, the browser POST fields, and Steps 10-22. [Interpretation] [EMV 3DS v2.2.0, sections 2.4.3-2.4.4, pp. 34-35; section 3.3, pp. 66-70, Reqs 117-140; sections A.5.3-A.5.4, pp. 224-226]

### 7.3 Browser session state, cookies, and protocol IDs

| State type | Specification treatment | Consequence |
|---|---|---|
| `threeDSServerTransID` | Protocol transaction identifier generated by the 3DS Server; the same value correlates Method data and later AReq. | It is the normative pre-AReq/AReq correlation key and is not a cookie. [EMV 3DS v2.2.0, section 3.3, p. 60, Reqs 81-83; section A.5.3, p. 224] |
| DS Transaction ID and stored 3DS Server URL | DS creates the ID and stores the Server URL with it for possible RReq routing. | This is server-side result-routing state, not browser navigation state. [EMV 3DS v2.2.0, section 3.3, pp. 62-63 and 69, Reqs 94, 99, and 130] |
| ACS Transaction ID and ACS retained IDs | ACS creates its ID and, for a browser challenge, stores Server/DS identifiers and DS URL for RReq. | ACS must retain transaction state even though DS and Server are absent from the direct browser-ACS HTTP path. [EMV 3DS v2.2.0, section 3.3, pp. 63-65, Reqs 104 and 109] |
| `threeDSSessionData` | Optional Requestor-defined Base64url session data passed with CReq and returned unchanged with CRes. It may be omitted if the Requestor can associate the final POST with the original session without it. | It correlates the browser return with Requestor session handling; it is opaque to the ACS and is not a protocol transaction ID. [EMV 3DS v2.2.0, section A.5.4, p. 226, Table A.3] |
| Browser cookies | Not specified in the analysed requirements. | **Implementation Inference:** a Requestor or ACS may use ordinary browser/server session mechanisms subject to its web architecture, but cookies must not be treated as a substitute for the specified EMV 3DS transaction identifiers.
