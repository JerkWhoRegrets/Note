# Error Handling

## Scope and evidence method

This analysis covers Section 5.9 on physical PDF pages 124-132. The source PDF is normative. The source map, analysis status, `docs/07-message-handling-and-timeouts.md`, and the relevant extracted text were read first; all nine in-scope pages were then rendered and inspected directly. Supplemental pages 112-119, 199, 205, 227-230, and 270 were inspected for the cross-cutting version, validation, timeout, `Erro`, and error-code definitions used below. [Interpretation; Descriptive (no modal)] [EMV 3DS v2.2.0, sections 5.1.4-5.5.2.3 and 5.9, pp. 112-132; sections A.4 and A.5.5, pp. 199, 205, and 227-230; section B.10, p. 270]

Section 5.9 contains no locally numbered requirements. Its receiving-party actions are written as present-tense processing directions rather than `shall` statements. They are recorded below as **Normative Processing Directions (unnumbered)**, without inventing requirement numbers or strengthening the source's modal language. Cross-cutting requirements from Sections 5.1-5.5 retain their printed requirement numbers. [Interpretation] [EMV 3DS v2.2.0, section 5.9, pp. 124-132]

Evidence labels are **Normative Requirement**, **Normative Processing Direction**, **Interpretation**, **Issuer ACS Implementation Consideration**, **Scheme or Vendor Dependency**, and **Unresolved**. No HTTP status code is stated anywhere in Section 5.9; the matrix therefore distinguishes an HTTP reply or browser POST where the specification identifies one, but never assigns an HTTP status code. [Normative Requirement plus Interpretation; Shall / not specified] [EMV 3DS v2.2.0, section 5.1.1, p. 111, Reqs 184 and 189; section 5.9, pp. 124-132]

## 1. Executive conclusions

1. **Error handling is receiver-specific and message-specific.** A component first recognises, verifies/decrypts where applicable, and validates the received message. Valid messages continue standard processing; invalid messages and received Error Messages follow the exception paths in Section 5.9. Business-logic exceptions remain in Chapter 3. [Normative Processing Direction; Will / Descriptive] [EMV 3DS v2.2.0, section 5.9, p. 124]
2. **The principal Section 5.9 validation codes are `101`, `201`, and `203`.** `101` covers a message that cannot be recognised, `201` a missing required element, and `203` a present element that fails validation. App CReq/CRes verification or decryption failure uses `302`. The detecting component identifies itself as `C`, `S`, `D`, or `A` in Error Component. [Normative Processing Direction plus table definition] [EMV 3DS v2.2.0, sections 5.9.1-5.9.12, pp. 124-132; section A.4, p. 199; section A.5.5, pp. 227-229, Table A.4]
3. **An `Erro` object can be a direct rejection, a forwarded error, or an input that triggers another protocol outcome.** Depending on the receiver and stage, the Error Message is returned to the immediate sender, passed onward unchanged, replaced by a DS-specific ARes, converted into RReq status `U` with Challenge Cancellation Indicator `06`, surfaced to the Requestor Environment, converted into a new ACS-to-SDK Error Message, or followed by a Browser CRes. [Normative Processing Direction] [EMV 3DS v2.2.0, sections 5.9.3-5.9.12, pp. 125-132]
4. **Transaction identification gates secondary routing.** Section 5.9 repeatedly conditions downstream notification on whether a specific transaction can be identified. The immediate sender still receives the prescribed rejection where the section says to return one; onward propagation, RReq generation, SDK notification, or Browser CRes generally occurs only when the transaction is identifiable. [Normative Processing Direction] [EMV 3DS v2.2.0, sections 5.9.3-5.9.12, pp. 125-132]
5. **App and Browser challenge error paths are deliberately different.** For App CReq errors, the ACS can return `Erro` directly to the SDK and, when identifiable, send RReq `U`/`06`. For Browser CReq errors, the ACS can return `Erro` through the browser only when the Notification URL is usable; an unrecognised message cannot yield that browser response because the URL cannot be extracted. [Normative Processing Direction plus footnote] [EMV 3DS v2.2.0, sections 5.9.5-5.9.6, pp. 126-128, source footnote 7]
6. **RRes errors do not rewrite an already determined challenge result in a uniform way.** For App, the ACS sends an Error Message to the SDK for an identifiable, non-Decoupled transaction; for Browser, it sends a CRes through the browser. The forwarding is suppressed for Decoupled Authentication, and the section does not define an alternative client notification. [Normative Processing Direction plus Unresolved] [EMV 3DS v2.2.0, sections 5.9.11-5.9.12, pp. 130-132]
7. **Unsupported version, timeout, malformed syntax, duplicate, and invalid-state cases come from cross-cutting rules and Table A.4, not from a complete restatement in Section 5.9.** Non-active versions use `102`; transaction version mismatch uses `203`; timeout uses `402`; invalid formatted or unrecognised messages fall under `101`; duplicate data elements, duplicate transaction IDs, and an already processed or incorrectly sent CReq are described under `204`, `301`, and `305`. Section 5.9 does not explicitly route all three duplicate/state codes, which remains an interoperability question. [Normative Requirement plus Unresolved] [EMV 3DS v2.2.0, sections 5.1.4-5.5, pp. 112-119, Reqs 195, 197-199, 208, 218, 220-227, 232, 235, 237, 239, 241-245, 312, 320, and 343-344; section A.5.5, pp. 227-230, Table A.4]

## 2. `Erro` message meaning and routing

The protocol Message Type token is `Erro`. The Error Message data set includes the 3DS Server, ACS, DS, and SDK Transaction IDs as applicable; Error Code, Error Component, Error Description, Error Detail, Error Message Type, Message Type, and Message Version Number. `errorMessageType` identifies the erroneous Message Type when that type is recognisable. [Table / Conditional] [EMV 3DS v2.2.0, section A.4, pp. 199 and 205; section B.10, p. 270, Table B.10]

Table A.4 says Error Messages are used to formulate a response when a message cannot be processed or when an error must be handled as part of receiving a response from another system. All components shall accept any Error Code value; if no Table A.4 entry matches, a reasonably close code shall be used; and codes `201`, `203`, `204`, and `304` require the erroneous element names in Error Detail. [Normative Requirement plus table guidance; Shall] [EMV 3DS v2.2.0, section 5.4, p. 115, Reqs 216-218; section A.5.5, p. 227, Table A.4]

In the matrix, “return” preserves Section 5.9's wording for the direct route back to the sender, while “send” preserves its wording for a secondary protocol route. Req 189 requires a corresponding response message to use the request POST's HTTP reply, but Section 5.9 does not say for every `Erro` route whether the Error Message is that corresponding response or a separately initiated message. ## 4. Message-specific analysis

### 4.1 AReq: DS and ACS

Both DS and ACS validate AReq against Table B.1, Section 5.1.6, and the Device Channel. Their error logic is symmetric except for Error Component and recipient: DS returns `D` errors to the 3DS Server, while ACS returns `A` errors to the DS. Section 5.9 assigns `101` for unrecognised, `203` for a present element that fails validation, and `201` for a missing required element. It does not prescribe a Transaction Status, retry, alternate ACS, or HTTP status code for these validation failures. [Normative Processing Direction plus Interpretation / evidence boundary] [EMV 3DS v2.2.0, sections 5.9.1-5.9.2, pp. 124-125]

### 4.2 ARes: DS and 3DS Server

The DS is both detector and intermediary. It rejects an invalid ARes back to the ACS, then, if it can identify the transaction, sends the 3DS Server either a DS-originated Error Message carrying the same code or an ARes with a DS-defined Transaction Status. When the ACS input is already `Erro`, the DS can pass it unchanged or convert it into DS-specific-status ARes. This choice and status mapping are scheme/DS dependencies, not issuer ACS behavior. The DS also logs transaction information as required by DS rules. [Normative Processing Direction plus Scheme or Vendor Dependency] [EMV 3DS v2.2.0, sections 5.9.3-5.9.3.2, pp. 125-126]

The 3DS Server rejects invalid ARes back to the DS and, when it can identify the transaction, informs the Requestor Environment. A received Error Message is surfaced to that environment; for App, the environment is expected to inform the SDK. No internal Requestor API, payload, HTTP status, retry, or recovery behavior is specified. [Normative Processing Direction plus Implementation Boundary] [EMV 3DS v2.2.0, section 5.9.4, p. 126]

### 4.3 CReq/CRes: App and Browser

App challenge messages add JOSE verification/decryption failure. An ACS that cannot verify/decrypt CReq uses `302`; an SDK that cannot verify/decrypt CRes also uses `302`. Recognition failures use `101`, content validation uses `201` or `203`, and an identifiable ACS-side CReq error results in RReq status `U` and cancellation `06`. [Normative Processing Direction] [EMV 3DS v2.2.0, sections 5.9.5-5.9.5.1 and 5.9.7, pp. 126-128]

Browser CReq is not described as JWE/JWS and Section 5.9.6 does not assign a `302` branch. For an unrecognised browser message, source footnote 7 says the ACS cannot extract the Notification URL, so no browser response is possible. For content failure, the response requires a valid Notification URL for code `203`, while the missing-required-element branch requires the URL to be present for code `201`. In either case, an identifiable transaction produces the same RReq `U`/`06` result path as App. [Normative Processing Direction plus source wording distinction] [EMV 3DS v2.2.0, sections 5.9.5.1-5.9.6, pp. 127-128, source footnote 7]

### 4.4 RReq: DS and 3DS Server

The DS rejects the RReq to the ACS and, if the transaction is identifiable, creates a second DS-originated Error Message to the 3DS Server with the same Error Code. Section 5.9.8.1 explicitly names the AReq-stored 3DS Server URL for App and Browser, but its cross-references are malformed and it does not cleanly state the 3RI route. The 3DS Server rejects an invalid RReq to the DS and informs the Requestor Environment; when the inbound message is already `Erro`, it only informs the environment. [Normative Processing Direction plus Unresolved] [EMV 3DS v2.2.0, sections 5.9.8-5.9.9, pp. 128-129]

### 4.5 RRes: DS and ACS in App and Browser

The DS rejects an invalid RRes back to the 3DS Server and, if it can identify the transaction, sends the ACS a DS-originated Error Message with the same code. A Server-originated Error Message is forwarded unchanged. The stated onward links cover App and Browser; Section 5.9.10 does not provide a separate 3RI/Decoupled client route. [Normative Processing Direction plus Interpretation / evidence boundary] [EMV 3DS v2.2.0, section 5.9.10, p. 130]

The ACS returns invalid RRes errors to the DS. For identifiable non-Decoupled App transactions it also sends the SDK an Error Message; an inbound Error Message is converted to a new ACS `403` error for the SDK. For identifiable non-Decoupled Browser transactions it sends CRes through the browser instead. Both subsections state that valid-RRes CRes status was already determined in the earlier flow, but do not restate the failure-branch Browser CRes fields/status. [Normative Processing Direction plus Unresolved] [EMV 3DS v2.2.0, sections 5.9.11-5.9.12, pp. 130-132]

## 6. Unresolved and dependency boundaries

### 6.1 Source and interoperability questions

- **Duplicate-element code conflict.** Table A.4 defines `204` for a duplicate data element and Req 218 requires element names in Error Detail, while every Section 5.9 “data element present fails validation” branch names `203`. The specification does not state whether the more specific table code overrides the repeated Section 5.9 route. Obtain EMVCo/DS clarification; do not silently select one by assumption. [Unresolved] [EMV 3DS v2.2.0, section 5.4, p. 115, Req 218; section 5.9, pp. 124-132; section A.5.5, p. 228, Table A.4]
- **Duplicate/invalid-state CReq routing.** Table A.4 assigns `305` when CReq reaches the wrong ACS, is inconsistent with ARes, or reuses an ACS Transaction ID already received and processed. Sections 5.9.5-5.9.6 name only `101`, `201`, `203`, and App cryptographic `302`, then prescribe RReq `U`/`06` for identifiable errors. The exact client-facing code and route combination for `305` is not stated. [Unresolved] [EMV 3DS v2.2.0, sections 5.9.5-5.9.6, pp. 126-128; section A.5.5, p. 229, Table A.4]
- **Duplicate Transaction ID route.** Table A.4 code `301` includes a Transaction ID recognised as a duplicate, but Section 5.9 does not name `301` or define a common replay/disposition algorithm. [Unresolved] [EMV 3DS v2.2.0, section 5.9, pp. 124-132; section A.5.5, p. 228, Table A.4]
- **3RI RReq forwarding cross-reference.** Section 5.9.8.1 says the 3DS Server URL is stored in Req 22 for App or Req 99 for Browser, then repeats `[Req 22]`; it does not state the 3RI stored-URL requirement or route even though RReq also exists in Decoupled 3RI. Treat the printed path as incomplete rather than inferring a new 3RI rule. [Unresolved] [EMV 3DS v2.2.0, section 5.9.8.1, p. 129, cross-referencing Req 22 at section 3.1, p. 48 and Req 99 at section 3.3, p. 63 as printed]
- **Browser Notification URL validity boundary.** Code `203` requires the Notification URL to be valid, code `201` requires it only to be present, and an unrecognised message yields no response because the URL cannot be extracted. The section does not specify the browser response when the URL is present but itself invalid, nor whether another identifiable route may be used. [Unresolved] [EMV 3DS v2.2.0, section 5.9.6, pp. 127-128, source footnote 7]
- **Failure-branch Browser CRes content.** Section 5.9.12 requires a CRes after unrecognised, invalid, missing-field, or received-Error RRes for an identifiable non-Decoupled transaction, but does not restate its Transaction Status or field set. The note about status previously determined is attached to the valid-RRes branch. [Unresolved] [EMV 3DS v2.2.0, section 5.9.12, pp. 131-132]
- **Decoupled RRes error completion.** Sections 5.9.11-5.9.12 suppress SDK/Browser notification for Decoupled transactions but do not state an alternative client-facing protocol outcome or retention/cleanup action after invalid RRes or received `Erro`. [Unresolved] [EMV 3DS v2.2.0, sections 5.9.11-5.9.12, pp. 130-132]

### 6.2 Scheme or implementation dependencies

- **DS error-to-ARes substitution.** Sections 5.9.3.1-5.9.3.2 let the DS send either Error Message or ARes with Transaction Status defined by that DS. The status mapping and selection rule require applicable DS rules. [Scheme or Vendor Dependency] [EMV 3DS v2.2.0, sections 5.9.3.1-5.9.3.2, pp. 125-126]
- **DS logging content.** Sections 5.9.3 and 5.9.10 require DS transaction logging according to DS rules but do not define log fields, retention, or access. This is not an ACS logging requirement. [Scheme or Vendor Dependency] [EMV 3DS v2.2.0, sections 5.9.3 and 5.9.10, pp. 125 and 130]
- **HTTP status and recovery behavior.** General message transport defines HTTP POST and reply pairing, but neither Section 5.9 nor its error-code table assigns HTTP status codes, retry-after behavior, cached-response replay, or a universal recovery rule. Those choices must not be represented as EMV 3DS requirements. [Implementation Decision] [EMV 3DS v2.2.0, section 5.1.1, p. 111, Reqs 184 and 189; section 5.9, pp. 124-132; section A.5.5, pp. 227-230, Table A.4]
