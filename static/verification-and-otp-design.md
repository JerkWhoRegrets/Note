# Verification and OTP Design for an Issuer ACS

## Purpose, evidence boundary, and labels

This document is an issuer-side implementation reference for verification methods, with OTP as the most detailed example. It is derived only from the EMV 3-D Secure Protocol and Core Functions Specification v2.2.0 PDF and the verified analyses in this project. It does not make an issuer API, OTP algorithm, delivery provider, database, or policy into an EMV 3DS requirement.

The labels used throughout are:

- **Normative EMV 3DS behavior** - a requirement, table rule, or normative processing direction in the source. Every such statement has a section, physical PDF page, and printed Requirement number when one exists.
- **Interpretive synthesis** - a bounded explanation assembled from cited normative routes or fields; it is not an additional requirement.
- **Reference issuer design - non-normative** - a concrete implementation recommendation, not prescribed by EMV 3DS.
- **Optional issuer API/event - non-normative** - an example private integration contract, never an EMV 3DS message.
- **Policy/external dependency** - a decision that requires issuer policy, a current EMVCo bulletin/erratum, a Payment System or DS rule, an SDK/certification profile, a PCI or regulatory requirement, or a vendor decision.

Source ambiguities and external dependencies are not silently resolved here. They remain in [Unresolved Questions](./unresolved-questions.md).

### A.2 Challenge preparation is distinct from challenge execution

#### A.2.1 Preparation

1. **Normative EMV 3DS behavior - App.** When the ACS chooses `C`, it sets Transaction Status `C`, selects an acceptable challenge method using at least the named SDK/device capability inputs, sets ACS Rendering Type, prepares the ACS-to-SDK secure channel, stores `sdkTransID` for later CReq processing, and stores `threeDSServerTransID` plus `dsTransID` for later RReq processing. [EMV 3DS v2.2.0, section 3.1, p. 50, Req 32]
2. **Normative EMV 3DS behavior plus unresolved internal actor - Browser.** When the ACS chooses a Browser challenge, it sets `C`, supplies the ACS URL, and stores `threeDSServerTransID`, DS URL, and `dsTransID` for later RReq processing. Req 117 assigns CReq creation/encoding/form posting to the 3DS Server, whereas Req 267 says the 3DS Requestor generates the CReq, iframe, and POST; the Browser -> ACS direct route is clear, but sole internal authorship is not. [EMV 3DS v2.2.0, section 3.3, pp. 64-67, Reqs 109-117; section 5.8.2, p. 123, Req 267]
3. **Normative EMV 3DS behavior - Decoupled, including App, Browser, and 3RI.** When the ACS chooses `D`, it confirms Decoupled Authentication, stores `threeDSServerTransID` and `dsTransID` for later RReq processing, starts the Requestor Decoupled Max Time timer, and authenticates the Cardholder outside the protocol. [EMV 3DS v2.2.0, section 3.1, pp. 50 and 55, Reqs 321-322 and 345-346; section 3.3, pp. 65 and 69, Reqs 325-326 and 347-348; section 3.4, pp. 75-77, Reqs 328, 330, and 349-354]
4. **Normative data-element rule.** `authenticationType` is ACS-sourced, is required in ARes when `transStatus` is `C` or `D`, and identifies Static (`01`), Dynamic (`02`), OOB (`03`), or Decoupled (`04`). [EMV 3DS v2.2.0, section A.4, p. 168, Table A.1; no local numbered Req]

Preparation therefore establishes protocol routing, challenge type, rendering, secure-channel material where applicable, retained correlation, and pending state. It does not itself prove that a code was generated, delivered, entered, or verified. **Interpretive synthesis.** [EMV 3DS v2.2.0, section 3.1, pp. 50-54, Reqs 32 and 45-61; section 3.3, pp. 64-68, Reqs 109-123; section 3.4, pp. 75-76, Reqs 328 and 330]

#### A.2.2 Execution

1. **Normative EMV 3DS behavior - App.** After the initial CReq, the ACS validates it, sets Interaction Counter to zero, sets Challenge Completion Indicator to `N`, obtains content for the selected method/UI type, and returns protected CRes. The SDK displays that CRes; Cardholder action then produces another protected CReq. [EMV 3DS v2.2.0, section 3.1, p. 53, Reqs 47-58]
2. **Normative EMV 3DS behavior - Browser.** After the one Browser CReq, the ACS validates it, sets Interaction Counter to zero, sends ACS HTML, receives Cardholder submissions through Browser HTTP traffic, and repeats HTML interfaces until it determines an outcome. [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 119-123]
3. **Normative EMV 3DS behavior - OOB.** The ACS supplies CRes instructions, authenticates the Cardholder through an issuer/service-provider channel outside the protocol, and obtains the result from that channel rather than from CReq. A same-device return can cause the SDK to post an acknowledgement CReq automatically; that acknowledgement is not the OOB authentication result. [EMV 3DS v2.2.0, section 3.2, pp. 57-58]
4. **Normative EMV 3DS behavior - Decoupled and 3RI.** App, Browser, and 3RI Decoupled flows have no CReq/CRes challenge path; authentication runs outside EMV 3DS and completion is reported by RReq/RRes. Non-Decoupled 3RI completes with ARes and has no interactive 3DS Client challenge. [EMV 3DS v2.2.0, section 2.7, p. 42; section 3.1, pp. 44 and 55, Decoupled note and Reqs 345-346; section 3.3, pp. 59 and 69, Figure 3.3 note and Reqs 347-348; section 3.4, pp. 71-77, Figure 3.4, Reqs 291, 298-299, 328, 330, 332-341, and 349-354]

### A.3 Verification-method and OTP lifecycle

#### A.3.1 Selection and result metadata

- **Normative EMV 3DS behavior.** For App challenge preparation, the ACS determines an acceptable method using at least Device Channel, Device Rendering Options Supported, and SDK Maximum Timeout. It also sets ACS Rendering Type. [EMV 3DS v2.2.0, section 3.1, p. 50, Req 32]
- **Normative data-element rule.** `acsUiType` values are Text (`01`), Single Select (`02`), Multi Select (`03`), OOB (`04`), and HTML (`05`) for App CRes. The standardized type is **Text**; "OTP" is the label in the sample/template material, not a separate UI Type. [EMV 3DS v2.2.0, section A.4, p. 165, Table A.1; section 4.2.3, pp. 87-89, Figures 4.8-4.9; section A.8, pp. 257-258, Table A.18; no local numbered Req]
- **Normative data-element rule.** `authenticationMethod` reports the approach used for the transaction: Static Passcode (`01`), SMS OTP (`02`), key-fob or EMV-card-reader OTP (`03`), App OTP (`04`), OTP Other (`05`), KBA (`06`), OOB Biometrics (`07`), OOB Login (`08`), OOB Other (`09`), Other (`10`), or Push Confirmation (`11`). It is conditionally required in the ACS-to-DS RReq only, is not forwarded in the DS-to-3DS Server RReq, and for 3RI appears only for Decoupled Authentication. [EMV 3DS v2.2.0, section A.4, p. 167, Table A.1; no local numbered Req]
- **Normative data-element rule.** `authenticationType` expresses planned/used class in ARes/RReq; `authenticationMethod` expresses the specific method in the ACS-to-DS RReq. The two fields are not interchangeable. [EMV 3DS v2.2.0, section A.4, pp. 167-168, Table A.1; no local numbered Req]

#### A.3.2 Generation and delivery

- **Interpretive synthesis / evidence boundary.** Figures 4.8-4.10 illustrate an OTP sent to a masked phone or email destination and a Single Select destination choice, but the source does not define an OTP-generation message, code format, secret store, issuer delivery API, provider protocol, delivery receipt, retry cadence, or fallback channel. Sample figure content is not a mandatory lifecycle. [EMV 3DS v2.2.0, section 4.2.3, pp. 88-90, Figures 4.8-4.10]
- **Normative App resend behavior plus interpretive boundary.** If the ACS permits Native Text/OTP resend, it supplies `resendInformationLabel`; when the Cardholder requests resend, the SDK sends CReq `resendChallenge`. `resendChallenge` asks the ACS to resend challenge information but does not state whether a new code is generated, which channel is used, or how many resends are permitted. [EMV 3DS v2.2.0, section 4.2.4, p. 95, Req 158; section A.4, pp. 210-211, Table A.1; section A.8, p. 257, Table A.18]
- **Normative Browser behavior plus interpretive boundary.** Browser challenge actions are ACS HTML/Cardholder submissions inside the one-CReq/one-CRes challenge. The source does not define a Browser `resendChallenge` field or Browser resend form schema. [EMV 3DS v2.2.0, section 3.3, pp. 67-68, Reqs 122-123; sections 2.4.3-2.4.4, pp. 34-35; section 4.3, pp. 102-108]

#### A.3.4 Verification, retries, and maximum attempts

- **Normative EMV 3DS behavior - App.** The ACS checks Cardholder-entered authentication data. On correct data, it increments Interaction Counter, sets `transStatus = Y`, applies DS-defined ECI and Authentication Value rules, and sets `challengeCompletionInd = Y`. [EMV 3DS v2.2.0, section 3.1, p. 54, Req 61]
- **Normative EMV 3DS behavior - App.** On incorrect data, the ACS increments Interaction Counter and compares it with the ACS maximum challenges. At or above that maximum it sets `transStatus = N`, `transStatusReason = 19`, the DS-defined ECI, and completion `Y`; below the maximum it prepares repeat-challenge information and returns to CRes. [EMV 3DS v2.2.0, section 3.1, p. 54, Req 61]
- **Normative EMV 3DS behavior - Browser.** Browser verification follows the same success/maximum logic, but retries are repeated ACS HTML interfaces and Browser submissions rather than repeated protocol CReq/CRes pairs. [EMV 3DS v2.2.0, section 3.3, p. 68, Req 123; sections 2.4.3-2.4.4, pp. 34-35]
- **Normative data-element rule.** `interactionCounter` is an ACS-tracked, two-character String representing the number of Cardholder authentication cycles attempted and is required in RReq for App and Browser. The row supplies no value range or padding rule. [EMV 3DS v2.2.0, section A.4, p. 202, Table A.1; no local numbered Req]
- **Interpretive synthesis / policy gap.** The Core source refers to the ACS maximum challenges but does not set its numeric value. It also sets no numeric resend limit or OTP delivery-retry limit. [EMV 3DS v2.2.0, section 3.1, p. 54, Req 61; section 3.3, p. 68, Req 123; section A.4, pp. 210-211, Table A.1]

#### A.3.5 Expiry and timeouts

EMV 3DS challenge timers are not an OTP-lifetime definition. The ACS and SDK must enforce the source timers below, while the source provides no separate code-validity period. **Normative timer behavior plus interpretive evidence boundary.** [EMV 3DS v2.2.0, sections 5.5.1-5.5.2.2, pp. 116-118, Reqs 219-227, 237, 239, 312, and 343-344]

| Timer | Owner/start | Normative expiry behavior | Citation |
|---|---|---|---|
| Initial CReq | ACS; starts when ARes `C` is sent | 30 seconds. On expiry the ACS sends RReq `N`, reason `14`, cancellation `05`, and clears any ephemeral key generated and stored for the current CReq/CRes exchange. A late initial CReq receives `Erro` component `A`, code `402`. | [EMV 3DS v2.2.0, section 5.5.1, p. 116, Reqs 219-222] |
| App continuation CReq | ACS; restarts after each successfully sent non-final CRes | 10 minutes/600 seconds. On expiry the ACS sends RReq `N`, reason `14`, cancellation `04`, and clears the ephemeral key. A late CReq receives `A/402`. | [EMV 3DS v2.2.0, section 5.5.1, p. 116, Reqs 223-225] |
| Browser challenge interface | ACS; starts after each successfully sent challenge interface | 10 minutes/600 seconds. On expiry the ACS sends RReq `N`, reason `14`, then CRes `N` to the Notification URL; the challenge completes. | [EMV 3DS v2.2.0, section 5.5.1, pp. 116-117, Reqs 226-227 and 343-344] |
| Per-App-CReq CRes read | SDK; starts after TLS handshake and full CReq send | 10 seconds. On expiry the SDK ends 3DS processing, sends ACS `Erro` component `C`, code `402`, and reports error to the App. | [EMV 3DS v2.2.0, section 5.5.2.2, p. 118, Reqs 237 and 239] |
| Whole App challenge | SDK; starts after TLS handshake and first CReq send | SDK Maximum Timeout is configured and cannot be less than five minutes. If final CRes is absent at expiry, the SDK ends processing and sends `C/402` to the ACS and an error to the App. | [EMV 3DS v2.2.0, section 5.5.2.2, p. 118, Req 312] |
| OOB App challenge | SDK/Requestor policy around the normative SDK timer | The Requestor should consider that OOB can take longer and adjust the SDK challenge timeout accordingly; the source gives no OOB-specific number. | [EMV 3DS v2.2.0, section 3.2, p. 58, source note; section 5.5.2.2, p. 118, Req 312] |
| Decoupled Max Time | ACS; starts for ARes `D` | Send one RReq immediately when a result is obtained. If no result exists at Max Time, send an RReq without a result, with the source's one-hour grace period. The 3DS Server waits at least Max Time plus 30 seconds. | [EMV 3DS v2.2.0, section 3.1, p. 55, Reqs 345-346; section 3.3, p. 69, Reqs 347-348; section 3.4, pp. 76-77, Reqs 349-354] |

#### A.3.6 Completion and final status

- **Normative App normal completion plus unresolved field-set cross-reference.** Once an outcome exists, the ACS sends RReq and receives a valid RRes through the DS; it then sends final protected CRes to the SDK. Req 76 requires Table B.5 and invokes Section 6.2.4.4, while that subsection names Table B.4 CRes data. The SDK validates CRes and returns the result to the App. Invalid RRes or inbound DS Erro instead follows the App Erro branch. [EMV 3DS v2.2.0, section 3.1, pp. 54-56, Reqs 62-79; section 5.9.11, pp. 130-131; section 6.2.4.4, p. 144; sections B.4-B.5, pp. 265-266, Tables B.4-B.5] [Related unresolved question](./unresolved-questions.md#source-ambiguity)
- **Normative Browser normal completion plus unresolved recipient/carriage.** Once an outcome exists, the ACS completes RReq/RRes first, then Base64url-encodes final CRes and causes the Browser to POST it to the supplied Notification URL in the Requestor Environment. Failure-CRes details, final carriage conflicts, and the terminating Requestor/3DS Server component remain unresolved. [EMV 3DS v2.2.0, section 3.3, pp. 68-70, Reqs 124-140; sections 5.9.6 and 5.9.12, pp. 127 and 131-132, source footnote 7; section A.4, p. 206, Table A.1; section A.5.4, p. 226, Table A.3] [Related unresolved questions](./unresolved-questions.md#source-ambiguity)
- **Normative OOB normal completion.** The ACS bases its decision on the OOB result, not the acknowledgement CReq, and then follows the standard RReq/RRes and final App CRes path when a valid RRes is received. [EMV 3DS v2.2.0, sections 3.1-3.2, pp. 54-58, Reqs 62-79]
- **Normative App timeout branches.** On initial-CReq timeout, the ACS sends RReq `N`/reason `14`/cancellation `05`, clears current ephemeral key material, and returns `A`/`402` to a late CReq. On continuation-CReq timeout it uses cancellation `04`, with the same result/error pattern. The source does not prescribe a normal final App CRes in either ACS-timeout branch. [EMV 3DS v2.2.0, section 5.5.1, p. 116, Reqs 219-225]
- **Normative Browser timeout branches.** On initial-CReq timeout, the ACS sends RReq `N`/reason `14`/cancellation `05`; a late CReq receives `A`/`402`, and the source does not prescribe a final CRes in that branch. On Browser challenge-interface timeout, the ACS sends RReq `N`/reason `14` and then sends CRes `N` to the Notification URL to complete the challenge. [EMV 3DS v2.2.0, section 5.5.1, pp. 116-117, Reqs 219-222, 226-227, and 343-344]
- **Normative Decoupled completion across App, Browser, and 3RI.** Exactly one RReq follows each ARes `D`; RRes acknowledges it, and no SDK/Browser final CRes is part of the Decoupled path. [EMV 3DS v2.2.0, section 3.1, pp. 55-56, Reqs 66-75 and 345-346; section 3.3, pp. 68-70, Reqs 128-137 and 347-348; section 3.4, pp. 76-77, Reqs 332-341 and 349-354]
- **Normative data-element rule.** App `challengeCompletionInd = Y` means no further challenge-message exchange is required and the ACS populates Transaction Status in CRes; `N` means more exchanges are required. It is protocol-cycle state, not a substitute for `transStatus`. [EMV 3DS v2.2.0, section A.4, p. 190, Table A.1; no local numbered Req]
- **Normative data-element rule.** Final CRes permits only `transStatus = Y` or `N`. The broader ARes/RReq values remain distinct, including `U`, `A`, `C`, `D`, `R`, and `I` under their message-specific conditions. [EMV 3DS v2.2.0, section A.4, pp. 216-217, Table A.1; section A.7.8, pp. 253-254, Table A.15; no local numbered Req]

### A.4 Flow-specific verification state-machine synthesis

The following compact state machines are **interpretive syntheses**, not new protocol states.

| Flow | State progression | Citation |
|---|---|---|
| App Native/HTML | Normal: `ARes transStatus=C / prepared` -> `wait initial CReq (30 s)` -> `CRes challengeCompletionInd=N / UI displayed` -> `wait entry, resend, cancel, or OOB acknowledgement (10 min per non-final CRes)` -> `verify` -> either `repeat CRes challengeCompletionInd=N` or `terminal result` -> `RReq/RRes` -> `final CRes challengeCompletionInd=Y and transStatus=Y or N` -> `complete`, subject to the Req 76 B.5 versus Section 6.2.4.4 B.4 field-set conflict. Initial timeout instead sends RReq `N`/`14`/`05`; continuation timeout sends RReq `N`/`14`/`04`; both clear the current ephemeral key, return `A`/`402` to a late CReq, and have no stated normal final App CRes. | [EMV 3DS v2.2.0, section 3.1, pp. 50-56, Reqs 32 and 40-79; section 5.5.1, p. 116, Reqs 219-225; section 6.2.4.4, p. 144; sections B.4-B.5, pp. 265-266] |
| Browser | Normal: `ARes transStatus=C / prepared` -> `wait one Browser CReq (30 s)` -> `ACS HTML interface (10 min per interface)` -> `Browser submit` -> either `repeat HTML` or `terminal result` -> `RReq/RRes` -> `final CRes POST` -> `complete`. Initial-CReq timeout sends RReq `N`/`14`/`05`, returns `A`/`402` to a late CReq, and has no stated final CRes; interface timeout sends RReq `N`/`14`, then CRes `N` to the Notification URL. | [EMV 3DS v2.2.0, section 3.3, pp. 64-70, Reqs 109-140; section 5.5.1, pp. 116-117, Reqs 219-222, 226-227, and 343-344] |
| App OOB | App progression through initial CReq/CRes -> `OOB instructions` -> `external OOB authentication pending` -> manual/automatic acknowledgement CReq -> ACS reads external result -> either updated OOB instructions or terminal result -> standard RReq/RRes and final CRes. | [EMV 3DS v2.2.0, section 3.2, pp. 57-58; section 3.1, pp. 54-56, Reqs 61-79] |
| App/Browser Decoupled | `ARes D` -> `external authentication pending until result or Max Time` -> exactly one `RReq` -> `RRes` -> `complete`; no CReq/CRes challenge execution. | [EMV 3DS v2.2.0, section 3.1, pp. 50 and 54-55, Reqs 321 and 62-66; section 3.3, pp. 65 and 68-70, Reqs 326 and 124-137; section 3.4, pp. 76-77, Reqs 349-354] |

### A.5 Duplicate, idempotency, and correlation boundary

- **Normative EMV 3DS behavior.** Response Transaction IDs, Reference Numbers, and other response fields defined by Table A.1 must match the corresponding request. [EMV 3DS v2.2.0, section 5.1.6, p. 114, Req 212]
- **Normative EMV 3DS behavior.** `threeDSServerTransID`, `acsTransID`, `dsTransID`, and `sdkTransID` are separately generated/assigned transaction identifiers; the source does not define them as equal or derivable. [EMV 3DS v2.2.0, section A.4, pp. 157, 164, 198, and 214, Table A.1; section 3.1, pp. 46-50, Reqs 3, 8, 16, 27, and 32]
- **Normative EMV 3DS behavior.** The ACS stores `sdkTransID` for App CReq processing and stores `threeDSServerTransID` plus `dsTransID` for later RReq processing in the named App, Browser, and Decoupled branches. [EMV 3DS v2.2.0, section 3.1, p. 50, Reqs 32 and 321; section 3.3, pp. 64-65, Reqs 109 and 325-326; section 3.4, p. 75, Req 328]
- **Normative EMV 3DS behavior.** The ACS must maintain ARes `C` transaction state so the corresponding CReq and timeouts can be processed. [EMV 3DS v2.2.0, section 5.5.1, p. 116, Req 219]
- **Normative error-code evidence plus interpretive unresolved boundary.** Table A.4 defines duplicate data element (`204`), duplicate/unrecognised Transaction ID (`301`), and already-processed or otherwise invalid CReq (`305`) conditions, but the source does not define a universal duplicate key, cached-response replay algorithm, or recovery after uncertain full-message delivery. ### B.3 Reference OTP lifecycle

1. **Reference issuer design - non-normative: select.** Resolve eligible methods after AReq validation/risk evaluation; ensure the selected method fits Device Channel and App rendering capabilities. Persist the decision before ARes. Do not call the issuer method service again merely because ARes delivery is retried.
2. **Reference issuer design - non-normative: create session.** Create one verification session per selected method/generation and bind it to the internal transaction key plus all present protocol IDs. Return an opaque `verificationSessionId`; never expose protocol-message construction to the credential service.
3. **Reference issuer design - non-normative: generate.** Ask the issuer credential service to create an OTP/passcode generation under issuer policy. Record only an opaque provider/credential reference or verifier representation, creation time, internal expiry, and generation number.
4. **Reference issuer design - non-normative: deliver.** Send to the policy-approved destination through a delivery adapter. Return CRes/UI instructions only after the coordinator has an internally consistent delivery state; define issuer behavior for delayed or failed delivery without inventing a protocol delivery-status field.
5. **Reference issuer design - non-normative: enter.** On App CReq or Browser form submission, normalize transport-specific input into an in-memory verification command. Do not write raw input to logs, traces, analytics, dead-letter payloads, or support screens.
6. **Reference issuer design - non-normative: verify.** Submit the entered value and session/generation reference to the credential service exactly once per issuer submission identity. Apply the result to the ACS state machine only if the transaction is still in the expected non-terminal phase.
7. **Reference issuer design - non-normative: retry.** Increment the protocol Interaction Counter according to the App/Browser flow and update the separate internal verification-attempt counter. Below the configured ACS maximum, produce the next CRes/HTML retry interface; at the maximum, commit the required `N`/`19` outcome.
8. **Reference issuer design - non-normative: resend.** Treat App `resendChallenge` or a Browser-private resend action as a request, not proof that delivery occurred. Enforce issuer rate/limit policy and choose explicitly whether resend rotates the generation or reuses it. Invalidate superseded generations consistently if rotation is chosen.
9. **Reference issuer design - non-normative: expire.** Reject an internally expired credential without confusing that event with an EMV 3DS timer. If the transaction is still active and attempts remain, apply issuer retry policy; if a protocol timer wins, commit the source-required timeout result and make all credential generations unusable for this transaction.
10. **Reference issuer design - non-normative: complete.** Atomically commit the terminal ACS result, render actual `authenticationType`/`authenticationMethod` consistently, create one semantic RReq outbox record, and prevent late verification, resend, OOB result, or Browser submission from reopening the transaction.

Protocol anchors for this lifecycle are the method selection, input, retry, timer, and result rules; the generation/delivery/session operations are private issuer design. [EMV 3DS v2.2.0, section 3.1, pp. 50 and 53-56, Reqs 32 and 47-79; section 3.3, pp. 67-70, Reqs 119-140; sections 5.5.1-5.5.2.3, pp. 116-119, Reqs 219-229, 231-237, 239-245, 312, and 343-344]

|---|---|---|

### B.5 Logging, privacy, and audit

- **Reference issuer design - non-normative.** Permit ordinary logs to contain protocol IDs, current phase, selected method codes, timer name/deadline, provider correlation, outcome class, and error code only under issuer access/retention policy.
- **Reference issuer design - non-normative.** Prohibit raw OTP/passcode, `challengeDataEntry`, `challengeHTMLDataEntry`, unrestricted Browser form bodies, credential verifier material, and full phone/email destinations from standard logs, traces, metrics labels, and support tooling.
- **Reference issuer design - non-normative.** Record an append-only audit event for method selection, credential generation reference, delivery request/result, submit receipt without raw input, verification outcome, attempt/resend increments, timeout, terminal result, each RReq send, and RRes/`Erro` receipt.
- **Reference issuer design - non-normative.** Keep protocol `interactionCounter`, internal verification attempt, resend, delivery, and provider counters separately auditable so the RReq value is not reconstructed from unrelated operational retries.

The source defines the sensitive challenge and correlation fields but does not prescribe the issuer/ACS logging or redaction implementation. It does separately require DS logging under rules defined by the DS in Reqs 36, 73, 113, 135, 296, 339, and 341; those DS duties do not supply an ACS redaction policy. [EMV 3DS v2.2.0, sections 3.1, 3.3, and 3.4, pp. 51, 56, 65, 69-70, 75, and 77, Reqs 36, 73, 113, 135, 296, 339, and 341; section A.4, pp. 167-168, 181-185, 191, 198, 202, and 214, Table A.1]

1. **Policy/external dependency - Text versus OTP terminology.** `acsUiType = 01` is Text, while Table A.18 and figures use OTP labels.
